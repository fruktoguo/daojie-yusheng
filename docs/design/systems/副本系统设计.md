# 副本系统设计

## 1. 目标与边界

副本和秘境是两套不同的地图与生命周期实现：

| 系统 | 地图 | 进入关系 | 生命周期 | 主要特点 |
| --- | --- | --- | --- | --- |
| 秘境 | 多玩家共享的大地图，地图随机生成 | 多个玩家可能同时进入同一张地图 | 长期运行或按秘境规则结束 | 探索、随机地形、玩家之间可能互相影响 |
| 副本 | 固定地图模板的独立实例 | 每个队伍单独创建一份实例 | 通关、失败或超时后销毁 | 流程固定、队伍隔离、随用随开 |

副本实例不能使用 `partyId` 直接作为实例 ID。使用独立的 `runId`，当前实现的实例 ID 格式为：

```text
dungeon:{runId}
```

队伍只是副本进入和成员快照的来源，不拥有跨场次复用的地图实例。

本阶段只设计以下三种流程：

1. 防守
2. 镇魔
3. 讨伐

暂不设计副本编辑器、随机副本生成、跨服副本和副本内玩家对抗。

## 2. 玩家精力

### 2.1 规则

新增独立的玩家资源“精力”，不与灵力、真元、生命、移动点数或属性中的“体力”混用。

- 最大储存：`240` 点。
- 恢复速度：每经过 `60` 分钟恢复 `1` 点。
- 恢复同时适用于在线和离线玩家。
- 精力达到上限后不继续累计。
- 进入副本时消耗精力；精力不足时拒绝创建副本实例。
- 精力消耗必须在副本实例成功激活前后形成一个原子操作，不能出现“实例已创建但没有扣除”或“扣除了但实例没有建立”的不一致。

建议内部字段使用 `stamina`，客户端和玩家界面显示为“精力”，不要复用 `qi` 等已有资源名。最终字段名在实现前固定下来。

### 2.2 恢复计算

不能依靠 1Hz tick 逐点增加，否则离线玩家不会自然恢复，也会增加无意义的运行时工作。建议持久化：

```ts
{
  stamina: number;
  staminaUpdatedAt: string;
}
```

读取或修改精力时，根据当前时间与 `staminaUpdatedAt` 计算完整的 60 分钟周期数：

```text
recoverable = floor((now - staminaUpdatedAt) / 60分钟)
newStamina = min(240, stamina + recoverable)
```

未满 240 点时，只消费已经实际补回的周期，保留不足 60 分钟的余数；达到 240 点后可以把时间基准推进到当前时间，避免长期满值后再次登录产生过大的无效周期数。

并发扣除时必须使用数据库事务、行锁或带版本条件的原子更新，不能先读后写覆盖其他请求。副本入口、重连恢复、GM 调整和其他未来精力消耗都应复用同一套资源服务。

### 2.3 已确认的精力消耗与退款

四种基础难度的精力消耗固定为：

| 难度 | 精力消耗 |
| --- | ---: |
| 试炼 | 4 |
| 困难 | 8 |
| 噩梦 | 12 |
| 现世 | 24 |

现世八阶不额外增加精力消耗，凡阶到帝阶均消耗 24 点。

只要队伍成功进入副本，就不退还精力。进入前任一成员精力不足、资格不满足或全员确认未完成，都不创建实例、不扣精力。扣除后如果基础设施导致实例根本没有成功激活，才允许走失败补偿，并记录审计。

## 3. 副本难度

### 3.1 四个基础难度

副本拥有四个基础难度：

| 显示名 | 建议稳定 ID | 说明 |
| --- | --- | --- |
| 试炼 | `trial` | 基础难度 |
| 困难 | `hard` | 提高敌人和流程压力 |
| 噩梦 | `nightmare` | 高压力挑战 |
| 现世 | `present` | 允许队伍额外选择世界阶位 |

具体数值不写死在通用流程代码中，应由副本 JSON 配置覆盖，例如怪物属性倍率、波次数量、房间强度、奖励倍率、时间限制和精力消耗。

### 3.2 现世八阶

只有 `present` 难度允许选择额外难度阶位，使用项目已有的八阶品质顺序：

| 阶位 | 稳定值 |
| --- | --- |
| 凡阶 | `mortal` |
| 黄阶 | `yellow` |
| 玄阶 | `mystic` |
| 地阶 | `earth` |
| 天阶 | `heaven` |
| 灵阶 | `spirit` |
| 圣阶 | `saint` |
| 帝阶 | `emperor` |

该字段表示“现世额外挑战阶位”，不直接等同于掉落物品质。副本可以通过配置把阶位映射到怪物强度、词缀、奖励和特殊机制，但不能默认把所有掉落物都提升到同阶。

推荐运行时使用：

```ts
{
  difficulty: 'present';
  presentRank: TechniqueGrade;
}
```

非现世难度的 `presentRank` 必须为空，由服务端校验，不接受客户端伪造任意组合。

### 3.3 难度与阶位属性计算（双轨制基准）

副本数值设计采用 **普通基准 / 极限基准 双轨制**：

#### 1. 普通难度系列（试炼、困难、噩梦）
以 **【普通标准基准】** 作为基础数值源，以 $2.00$（$100\%$ 翻倍）为全属性步进，生命额外逐级翻倍：

| 难度 | `difficultyStep` | 全属性倍率 | 生命额外倍率 | 最终总生命倍率 (相对普通基准) |
| --- | ---: | ---: | ---: | ---: |
| 试炼 (`trial`) | 0 | `1.00x` ($2.00^0$) | `1.0x` | **`1.00x`** |
| 困难 (`hard`) | 1 | `2.00x` ($2.00^1$) | `2.0x` | **`4.00x`** ($2.00 \times 2$) |
| 噩梦 (`nightmare`) | 2 | `4.00x` ($2.00^2$) | `4.0x` | **`16.00x`** ($4.00 \times 4$) |

#### 2. 现世极境系列（凡阶至帝阶 8 阶）
以 **【极限极境基准】** 作为基础数值源，以 $1.20$（$+20\%$）为全属性步进；凡阶基础生命额外 10 倍，后续每阶逐级翻倍；现世副本怪物的 **闪避、暴击、免爆、拆招（化解）** 4项二级属性减半（0.5x）：

| 现世阶位 | `rankStep` | 全属性倍率 (相对极限) | 生命额外倍率 | 最终总生命倍率 (相对极限基准) |
| --- | ---: | ---: | ---: | ---: |
| 凡阶 (`mortal`) | 0 | `1.00x` ($1.20^0$) | `10x` | **`10.00x`** |
| 黄阶 (`yellow`) | 1 | `1.20x` ($1.20^1$) | `20x` | **`24.00x`** |
| 玄阶 (`mystic`) | 2 | `1.44x` ($1.20^2$) | `40x` | **`57.60x`** |
| 地阶 (`earth`) | 3 | `1.728x` ($1.20^3$) | `80x` | **`138.24x`** |
| 天阶 (`heaven`) | 4 | `2.0736x` ($1.20^4$) | `160x` | **`331.78x`** |
| 灵阶 (`spirit`) | 5 | `2.4883x` ($1.20^5$) | `320x` | **`796.26x`** |
| 圣阶 (`saint`) | 6 | `2.9860x` ($1.20^6$) | `640x` | **`1911.03x`** |
| 帝阶 (`emperor`) | 7 | `3.5832x` ($1.20^7$) | `1280x` | **`4586.47x`** |

精力消耗不随现世阶位变化，现世始终消耗 24 点。每个副本可以通过 JSON 覆盖上述默认规则。

## 4. 总体架构

副本实现拆成“通用运行骨架、JSON 数值配置、单副本流程控制器”三层。

### 4.1 通用运行骨架

通用层负责所有副本都需要的能力：

- 队伍资格校验和成员快照。
- 难度、现世阶位和精力消耗校验。
- 精力恢复计算与原子扣除。
- 固定地图模板实例化。
- `runId` 分配、状态机和超时处理。
- 玩家进入、离开、断线重连和重新同步。
- 副本内实体、房间、出口和奖励的实例隔离。
- 实例能力必须显式声明：默认关闭队伍间 PvP 和地图破坏，不依赖地图预设名称推断。
- 通关、失败、取消、超时的幂等结算。
- 结算审计、奖励发放和实例销毁。

建议抽象：

```ts
interface DungeonFlowController {
  onRunCreated(ctx: DungeonFlowContext): void;
  onPlayerEnter(ctx: DungeonFlowContext, playerId: string): void;
  onTick(ctx: DungeonFlowContext): void;
  onEntityDeath(ctx: DungeonFlowContext, entityId: string): void;
  onRoomEvent(ctx: DungeonFlowContext, event: DungeonRoomEvent): void;
  onPlayerLeave(ctx: DungeonFlowContext, playerId: string): void;
  onAbort(ctx: DungeonFlowContext, reason: DungeonAbortReason): void;
}
```

控制器实例必须绑定单个 `runId`，不能把波次、房间进度、Boss 状态放在全局单例中。

### 4.2 JSON 配置

JSON 只负责稳定、可校验的内容和数值，不承载任意脚本执行：

- 副本 ID、名称和流程类型。
- 地图模板和房间连接关系。
- 难度覆盖和现世八阶参数。
- 精力消耗、时间限制、波次或房间数。
- 怪物生成组、Boss/精英引用。
- 奖励表、首通规则和结算参数。
- 机制流程控制阵法的类型、强度系数和可解除规则。

服务启动时完成 schema 校验和索引构建；运行中的 tick 只读取预解析结构。JSON 不应包含 TypeScript 代码、动态表达式或任意函数名调用。

### 4.3 单副本脚本

每个具体副本拥有自己的流程控制器脚本，负责该副本独特的规则和事件顺序。例如某个镇魔副本可以有特殊 Boss 击杀顺序、隐藏房间或特殊封界条件，但这些逻辑不能塞进 JSON 的通用字段中。

可复用的能力应沉淀为模块，而不是复制粘贴：

- `DungeonRunService`：运行实例和生命周期。
- `DungeonDifficultyService`：难度归一化和数值合并。
- `DungeonRoomService`：房间开启、关闭和路线推进。
- `DungeonWaveService`：波次生成和波次计时。
- `DungeonRewardService`：幂等结算和奖励发放。
- `MechanismFormationService`：由机制流程控制的通用阵法能力。

## 5. 三种流程

### 5.1 防守

防守副本全程使用一个小型固定地图，玩家没有必须移动的流程目标。

流程：

1. 创建实例并生成防守区域。
2. 按配置等待波次间隔。
3. 生成当前波次的怪物。
4. 当前波次清空后，进入下一波等待或立即生成。
5. 全部波次完成并满足结算条件后通关。

JSON 至少应支持：

- 波次总数。
- 每波生成组和数量。
- 波次间隔。
- 同时存在上限。
- 难度和现世阶位的强度倍率。
- 波次失败、超时和提前结束规则。
- 每波奖励、通关奖励和额外评价奖励。

### 5.2 镇魔

镇魔副本由多个直线连通的房间组成，每个房间有一个 Boss。

流程：

1. 只开放第一个房间。
2. 进入房间后生成该房间 Boss 和封界阵。
3. Boss 被击杀，或玩家主动拆毁封界阵后，房间出口开启。
4. 玩家通过出口进入下一个房间。
5. 所有 Boss 完成后通关。

如果当前房间已经是最后一个房间，Boss 击杀或机制阵法拆毁应直接触发副本通关，不要求必须再存在一个实际出口。

房间状态必须由服务端控制，不能让客户端通过修改地图出口状态绕过流程。新成员也不能通过重新进入直接获得未解锁房间的权限。

### 5.3 讨伐

讨伐副本同样由多个直线连通的房间组成，但没有 Boss，只有小怪和精英怪。

流程：

1. 只开放第一个房间。
2. 进入房间后生成该房间的小怪和精英怪。
3. 满足房间清理条件后开启下一段路线。
4. 重复直到所有房间完成并结算。

讨伐的房间清理条件、精英数量和奖励应配置化，但不应复用“Boss 死亡”作为通用完成条件。

### 5.4 首个副本：唤灵真人

首个实际副本使用镇魔流程，但只设计一关，用于验证完整链路：

- 副本 ID：`dungeon_huanling_zhenren`。
- 流程类型：`suppress_demon`。
- 房间数量：1 个。
- 房间内容：Boss“唤灵真人”和一个机制流程控制阵法。
- Boss 数据和技能：以独立 Boss 模板完整写入，与现有“重伤版本”保持一致，但不直接引用其配置文件。
- 特殊差异：不施加“重伤”Buff。
- 难度变化：首版只有属性增幅，不新增技能、特性或特殊词缀；现世最高开放到灵阶，阶位按有效属性等级额外计算。
- 封界阵拆毁：与 Boss 击杀一样直接算通关，立即进入结算状态并向队伍弹出结算菜单。

副本 Boss 模板不携带重伤 Buff；地图模板、Boss 配置和奖励均使用独立副本 ID 管理，不能直接修改或运行时引用原有破败洞府内容。

该副本的现世最高阶配置为灵阶。圣阶和帝阶仍保留在共享阶位枚举中，但本副本不可选择。

## 6. 机制流程控制阵法（通用能力）

封界阵不应设计成镇魔副本的专用特例。后续凡是需要划定范围、封锁区域、限制通行、维持场地效果或等待机制事件的玩法，都可以创建同一种“机制流程控制阵法”。镇魔封界阵只是该能力的第一个使用场景。

该能力的职责边界是：阵法系统负责范围效果、灵力/耐久表现和受击结果；副本控制器或其他机制流程负责何时创建、何时改变状态、何时开启通路以及何时销毁。

潜在使用场景包括：

- 副本房间封锁和路线解锁。
- 防守玩法的保护区域、核心区域或刷怪边界。
- 任务、活动或世界事件的阶段范围。
- Boss 阶段场地、禁入区和临时安全区。
- 需要持续一段时间、由机制条件解除的区域效果。

### 6.1 与普通阵法的区别

机制流程控制阵法不是玩家可自由部署、切换和拆除的普通阵法，而是由流程控制器创建的临时或持久机制对象。它可以复用阵法的范围效果和灵力表现，但必须使用独立控制模式：

- `source = dungeon_controller | quest_controller | event_controller | world_mechanism`
- `controllerId =` 创建它的具体流程控制器实例。
- `controlMode = controller_only`
- `arrayEyeMode = none`
- 不生成玩家可选中的普通阵眼。
- 不接入普通阵眼开关、拆阵和管理面板。
- 生命周期绑定创建它的机制实例；副本场景下还必须绑定当前房间和 `runId`。

建议由通用服务提供以下操作，而不是让每个玩法直接修改阵法内部字段：

```ts
createMechanismFormation(input): MechanismFormationId;
updateMechanismFormation(id, patch): void;
disableMechanismFormation(id, reason): void;
destroyMechanismFormation(id, reason): void;
```

控制器可以决定阈值、触发条件和状态转换，但不能绕过阵法服务直接改地图碰撞或玩家状态。阵法服务也不能自行推进副本房间、发奖励或结束流程。

如果底层实现必须存在一个锚点，锚点只能是服务端内部句柄：无坐标交互入口、不可选中、不可攻击、不可被玩家控制，也不能被普通阵法 API 当成阵眼处理。

### 6.2 镇魔封界阵用例

镇魔房间使用 `kind = room_seal` 的机制流程控制阵法，完整套住当前房间。它的强度与解除条件由镇魔控制器提供，通用阵法服务只负责执行范围效果和灵力变化。

封界阵灵力总量为该房间 Boss 最大生命值的 `100` 倍：

```text
barrierPower = bossEffectiveMaxHpAtRoomStart * 100
```

建议在房间激活时记录 Boss 的有效最大生命值并计算一次，避免战斗中动态属性变化导致封界阵强度漂移。封界阵可以被玩家直接攻击；其灵力归零后视为被拆毁。当前房间不是最后房间时开启出口，最后房间则直接触发副本通关。

出口开启条件为以下任一条件满足：

- 房间 Boss 被击杀。
- 封界阵灵力降为 0。
- 副本控制器明确触发特殊通关事件。

Boss 击杀和拆阵必须由镇魔控制器调用同一个幂等的“房间解锁/通关”操作，避免重复发奖励、重复开门或重复推进房间序号。其他玩法可以使用不同的解除条件，但仍应通过同一套机制阵法状态接口完成。

### 6.3 范围效果与表现规则

机制流程控制阵法必须直接复用普通阵法的效果解析和范围规则；镇魔首版使用 `boundary_barrier` 控制房间通路，后续可直接使用固脉、聚灵、怪物压制、视野压制等已有阵法效果。以下表现不能由普通阵眼逻辑隐式推断：

- 是否阻挡房间内技能和远程投射物。
- 是否阻挡视野、仇恨或 AOI。
- 阵法被拆毁或失效时是否产生特殊战斗事件。
- 机制完成后阵法是立即销毁，还是保留为已失效表现。

机制阵法的“特殊”只限于阵眼不可交互、控制权归流程控制器以及生命周期随机制实例变化；具体效果仍由普通阵法效果类型决定，不在副本控制器中复制一套效果计算。

## 7. 生命周期与结算

副本状态建议至少包含：

```text
created -> activating -> active -> completing -> completed
                                  \-> failed / aborted / expired
```

关键约束：

- 精力在实例激活流程中原子扣除。
- 结算使用唯一 `completionId` 或等价幂等键。
- 奖励发放成功后才能标记 `completed`。
- 进入 `completing` 后冻结副本战斗和流程推进，生成结算快照并向全体队员发送结算菜单；结算菜单只负责展示，奖励真源仍在服务端。
- 进入 `completed`、`failed`、`aborted` 或 `expired` 后禁止继续产生战斗和掉落。
- 实例销毁必须清理地图实体、房间状态、机制流程控制阵法和临时索引。
- 销毁后保留必要的运行摘要和结算审计，不保留可继续运行的地图状态。

队伍成员在创建时冻结。玩家进入副本后，副本不再管理队伍本身；队伍的在线状态不影响副本是否继续运行。运行中不允许临时加入新成员，已退出副本的玩家也不能重新进入。

## 8. 入口和队伍规则

副本不从组队面板直接发起。入口地图放置并显示忆梦石实体，队长必须在忆梦石附近发起；服务端同时校验队伍成员仍位于入口地图和队长距离，客户端入口仅用于展示。

发起后打开队伍准备界面：每行显示玩家单字名称、境界和准备状态，玩家只能勾选自己的复选框，所有状态通过 `DungeonEntryPrompt` 实时同步。全员准备后开始 5 秒倒计时，倒计时内任何成员取消准备都会回到准备阶段；倒计时结束重新校验队伍、位置和精力，成功后才创建副本实例并扣除精力。

已确认规则：

- 队伍最多 5 人，副本完全受现有队伍控制，不另行接管队伍管理。
- 队伍全员必须位于副本入口所在地图，不要求站在同一坐标附近。
- 由队长发起进入请求。
- 其他队员收到确认弹窗，全部队员确认后才继续创建实例。
- 确认期间任何成员离开入口地图、离开队伍或资格失效，都使本次进入失败。
- 服务端在全部确认后冻结成员快照并统一校验精力、等级、任务和其他资格。
- 只要有成员精力不足或资格不满足，就不创建实例、不扣任何成员精力。
- 创建成功后为该队伍分配独立 `runId`，其他队伍不可看见或进入该实例。
- 成功进入后，玩家是否在线不影响实例继续运行，除非副本自己的流程配置明确要求在线玩家数量。
- 退出副本必须在副本入口旁边执行；退出后永久失去本次副本的进入资格。
- 副本运行中不能加入新成员，不能在副本内退出队伍、解散队伍或踢出队员。
- 玩家必须先退出副本，才能进行离队、解散或踢人等队伍操作。
- 队长离开队伍时，队长自动移交给其他现存队员；副本内不允许触发离队，因此该规则在副本外生效。

进入确认请求应有过期时间，过期后需要队长重新发起；具体时长可以作为通用入口配置。

## 10. 当前实现落点

通用运行骨架由 `DungeonRuntimeService`、`DungeonFlowController`、`DungeonMechanismFormationService`、`DungeonRewardService` 和 `DungeonRunPersistenceService` 组成。实例 tick 在世界实例编排器中调用流程控制器；房间和波次生成均从已校验 JSON 读取，怪物属性在生成时按有效阶位指数倍率归一化。

机制阵法通过普通阵法服务计算范围、边界伤害和灵力耗尽，但以 `source=dungeon_controller`、`controlMode=controller_only`、`arrayEyeMode=none` 标记，玩家不能操作阵眼；流程控制器收到阵法耗尽事件后负责开路或结算。

副本流程快照写入 `dungeon_run`，终态保留为审计记录，运行态实例仍在通关后等待队员从入口撤离；全员撤离或超时清理后销毁临时实例。奖励服务使用 `completionId` 做幂等键，配置的 `itemRewards` 在结算前发放，Boss 原有掉落继续沿用战斗掉落链路。

## 11. 验证计划

实现阶段至少需要以下最小验证：

1. 精力恢复：在线、离线、未满 60 分钟、跨多个周期、达到 240 上限。
2. 精力扣除：精力不足拒绝进入，并发进入只能成功扣除一次。
3. 难度：四种基础难度以及现世八阶的合法性校验。
4. 隔离：两个队伍使用相同副本模板时，实体、房间进度、机制流程控制阵法和奖励互不影响。
5. 防守：波次间隔、数量、清波推进、超时和结算幂等。
6. 机制阵法与镇魔：Boss 击杀和直接拆阵都能触发最后房间通关，自动弹出结算菜单，无阵眼控制，重复触发不重复结算；其他流程可复用同一机制阵法服务。
7. 讨伐：小怪和精英清理开路，流程中不存在 Boss 依赖。
8. 生命周期：通关或失败后实例销毁，销毁后不能继续战斗、移动或领奖。
9. 断线重连：重连后恢复当前副本、难度、房间和流程状态；已通关但未查看结算的玩家能收到结算快照。

## 12. 已冻结规则

本阶段已经冻结：

1. 精力上限 240，60 分钟恢复 1 点。
2. 难度精力消耗为 4、8、12、24，现世八阶统一 24 点。
3. 队伍最多 5 人，全员在入口地图，由队长发起，所有人确认后进入。
4. 进入后副本不接管队伍，在线状态不影响实例继续运行。
5. 退出必须在入口旁边执行，退出后不能重进，不能中途加入。
6. 副本内不能离队、解散或踢人，队长离队时自动移交。
7. 机制流程控制阵法复用普通阵法效果，仅移除玩家对阵眼的交互和管理。
8. 唤灵真人首版只有属性增幅，技能复用重伤版本但不带重伤 Buff。
9. 难度和现世阶位共同计算有效属性等级；每增加一阶，全属性乘 `1.2`，生命在全属性倍率之外再乘 `2`。
10. 唤灵真人单关副本中，Boss 被击杀或机制阵法被拆毁都算通关，立即进入结算状态并弹出结算菜单。
