# 秘境系统设计

> 状态：**设计稿，未实现**。本文只固化设定与引擎事实基线，不含实现步骤。
> 最后更新：2026-07-09

## 1. 目标形态

玩家踏入传送阵时，服务端按 `seed + 秘境等级 L` 现场生成一整张含地形、怪物、宝箱、草药、秘籍的地图，
创建实例，无人工干预。同一 `(seed, L)` 永远生成同一张图。

秘境不是一张更大的野外地图，而是**分区拼装**的关卡：外围开放地貌、中层迷宫、深处地牢，
区与区之间靠走廊或传送阵相连，区域数随地图面积增长（不是固定 2 栋房子）。

## 2. 已敲定的上位决策

| 维度 | 决策 |
|---|---|
| 布局范式 | **分区拼装**。一张图切成若干区域，每区用不同生成器；区域数随面积长 |
| 内容耦合 | **骨架强耦合 + 填充弱耦合**。先用图规划关卡拓扑（入口→战斗房→宝库→boss→出口），关键奖励挂拓扑节点；普通草药/杂兵按地形查表撒 |
| 交付形态 | **运行时全自动**。踏阵即生成，无人工 |
| 秘籍产出 | **后台预生成功法池**。worker 持续用 `executeGeneration` + `publishGeneratedTechnique` 造已发布的 `gen_*`，按 grade/realmLv 分档入池；秘境创建时按 seed 从池里抽，零延迟 |
| 藏书阁形态 | **摆 N 个藏经台，各存一门**。服务端在宝库房间 seed 出 N 个 `scripture_platform` 建筑实例，各写入一门已发布的 `gen_*` |
| 怪物池 | 杂兵与精英复用现有怪物，boss 专属且走 AI 生成 |
| 刷怪时机 | 小怪与精英按区域触发（玩家首次踏入该区才注入），boss 建实例时一次性刷 |
| 地形血量 | 在现有 `1.4^(mapLv−1)` 基础上再乘 `1.1^(L−1)` |
| 复生规则 | 地形拆除后**永不复生**，但保留 1%/息 自然回血；怪物击杀后**永不复活** |

## 3. 数值口径

### 3.1 地形血量

```
maxHp = 100 × 1.4^(L−1) × 1.1^(L−1) × 材质倍率
      = 100 × 1.54^(L−1) × 材质倍率
```

| L | 1.54^(L−1) | 墙(×50) maxHp | 1%/息 回血 |
|---|---|---|---|
| 5 | ×5.6 | 2.8 万 | 280 |
| 10 | ×44.6 | 22 万 | 2200 |
| 20 | ×3487 | 1743 万 | 17 万 |
| 30 | ×27.3 万 | 13.6 亿 | 1360 万 |

⚠️ **已知数值后果**：20 级以上，墙的自然回血超过多数玩家 DPS，拆墙事实上不可能，
「拆了不复生」这条规则在深层秘境失去意义。若希望深层墙「打得动但打得慢」，底数应压到 1.2 上下。

### 3.2 怪物强度

引擎现有曲线（`packages/shared/src/combat.ts:51-54`）：

```
getRealmAttributeMultiplier(level) = 1.1^(level−1)     // REALM_ATTRIBUTE_GROWTH_RATE = 0.1
```

**普通怪与精英怪：`level = L` 即可，「每级额外 10% 指数生命值」天然满足，零改动。**

boss 要求「每级 20% 指数」，通过换算 level 实现，同样零改动：

```
1.1^(Lb−1) = 1.2^(L−1)   ⟹   Lb = 1 + (L−1) × 1.9136
```

| L | boss level | boss 实际倍率 | 目标 1.2^(L−1) | 误差 |
|---|---|---|---|---|
| 10 | 18 | ×5.05 | ×5.16 | −2.1% |
| 20 | 37 | ×26.4 | ×26.6 | −0.8% |
| 30 | 56 | ×132 | ×137 | −3.6% |

### 3.3 tier 与 HP 倍率

`MonsterTier` 只有三档（`packages/shared/src/world-core-types.ts:479`），恰好对上杂兵/精英/boss：

| tier | 中文 | `MONSTER_TIER_HP_MULTIPLIERS` | `TIER_BASE_RATIOS` | 用途 |
|---|---|---|---|---|
| `mortal_blood` | 凡血 | ×1 | 0.5 | 杂兵 |
| `variant` | 异变 | ×2 | 0.8 | 精英 |
| `demon_king` | 妖王 | ×10 | 1.0 | boss |

常量位置：`packages/shared/src/monster.ts:649-659`。

> ⚠️ 项目内**没有** `'boss'` 这个 tier。`world-runtime-auto-combat.service.ts:437` 的 `case 'boss'`
> 是自动索敌的偏好模式，与 `MonsterTier` 无关。

## 4. 引擎事实基线

以下全部经代码核实（非文档、非注释推测），是设计的硬约束。

### 4.1 运行时动态注册地图：可行，有两个先例

`MapTemplateRepository.registerRuntimeMapTemplate(document)`（`packages/server/src/runtime/map/map-template.repository.ts:143`）
把内存里的 `GmMapDocument` 注册成模板。通天塔每层、宗门驻地都在用。

- 接受 `format:2` 的 `terrain/surface/structure` 中文字符行（经 `preprocessFormatV2` 解码），
  也接受旧的 `tiles: string[]`。procgen 当前产出的三层格式**可以原样喂进去**。
- 这条路径**不跑** `assertRuntimeMapDocumentV2`，**不跑** `validateEditableMapPortalReciprocity`。
- **坐标越界一律静默 clamp 或丢弃，不报错、不打日志。** 生成器必须自校验落点。

### 4.2 白名单重建：自定义字段会无声蒸发

`normalizeEditableMapDocument`（`packages/shared/src/map-document.ts:833-1063`）不是「透传 + 删字段」，
而是**从零构造一个只含白名单字段的新对象**。任何未被显式列举的键（包括 `_procgenContent` 这类下划线字段、
`terrainProfileId` 等）在这一步永久消失。

> 全仓**未找到**任何 `startsWith('_')` 的过滤代码——下划线字段失效纯粹是白名单重建的副作用。

**结论：秘境的一切内容必须落在标准顶层字段里。**

### 4.3 怪物：`monsterSpawns` 对动态图完全无效

- `MapTemplateRepository` 全文**零次**读取 `monsterSpawns`。
- 怪物走另一个仓库 `ContentTemplateRepository`，它的 `buildFallbackMonsterRuntimeStatesForMap`
  会**重新 `findMapDocumentFile(mapId)` 读磁盘上的地图 json**。内存图没有盘文件 → 返回 null → 一只怪都没有。

**正确做法（照抄通天塔）**：注册模板时 `monsterSpawns: []`，建完实例后逐只
`instance.addRuntimeMonster(contentTemplateRepository.createRuntimeMonsterSpawn(monsterId, {...}))`
（`world-runtime-tongtian-tower.service.ts:591,606`）。

因此**生成器必须产出两样东西**，不是一样：

1. `GmMapDocument` —— 地形三层 + `landmarks[]`（宝箱与草药）+ `portals` + `spawnPoint`
2. **怪物注入清单** —— `{ monsterId, x, y, level, tier, regionId }[]`，实例建好后按区域触发注入

### 4.4 怪物只能引用已冻结的 97 个 monsterId

`data/content/monsters/*.json` 在启动期加载并冻结，运行时**无法注入新怪种或新掉落表**。
怪物掉落一律内联在 catalog 的 `drops[]`，按 `monsterId` 索引（`monsterDropsByMonsterId`）。
刷新点上内联的 `drops` / `attrs` / `skills` / `hp` / `attack` 等字段是**死字段**，运行时刷怪链路一概不读。

> 97 个模板全部带 `attrTendency` → `statFormula` 全覆盖 → `level` 覆盖必然生效。

### 4.5 宝箱与草药是同一样东西

都是 `landmarks[i].container`，靠 `variant` 区分：`'herb'` = 草药，缺省 = 宝箱。
运行时容器集合 = `landmarks.flatMap(l => l.container ? [l.container] : [])`
（`map-template.repository.ts:317-320`）。

- 地图文档的 `resources` 字段**与采集无关**，它是逐格灵气分布，非 qi key 会被 `parseQiResourceKey` 丢弃。
- `InteractableKind.Container / Formation / Mechanism` **无任何运行时逻辑**，只是编辑器调色板标签。
- landmark 缺 `id`/`name`/`x`/`y` 或坐标越界会被**静默丢弃**（`map-template.repository.ts:734-741`）。
- 草药采完不消失，按 `refreshTicksMin/Max` 重生；**若模板不配这两个字段，采完就永不重生**。
- 灵气/风水**不影响**草药产出或刷新（两条独立链路）。想「灵气浓的地方长好草药」，必须生成器自己建立关联。

### 4.6 `container.lootPools` 永远 roll 不出秘籍

`matchesLootPoolFilters` 第一道门（`drop-table.registry.ts:471-473`）：

```ts
const gradeOrder = resolveTechniqueGradeOrder(item.grade);
if (gradeOrder === null) { return false; }
```

所有 `skill_book` 模板**都没有模板级 `grade` 字段**（书的品阶从它教的功法派生，那条派生路径只服务怪物掉落）。
因此**所有秘籍在第一道门就被排除**。`minGrade/maxGrade/tagGroups` 这套池子是给丹药/装备/材料用的。

**连带的坑**：`generateContainerEntries` 里
`if (entries.length > 0 || container.lootPools.length > 0) return entries;`
—— 只要容器带了 `lootPools`，`drops` 就被**完全短路**，哪怕池子一件都没 roll 出来。
产书的宝箱不能同时挂池子。

### 4.7 AI 功法生成：服务端可内部调用，但强依赖 LLM

`TechniqueGenerationService`（`packages/server/src/runtime/technique-generation/technique-generation.service.ts`）
的职责是分层的：

| 方法 | 玩家绑定 | 说明 |
|---|---|---|
| `requestGeneration(params)` :124 | **强绑定** | 扣悟道玉简、写 job 审计、roll 品阶/境界、失败返还 |
| `executeGeneration(jobId, params)` :212 | **弱绑定** | 纯生成内核。不 roll、不扣道具、不发通知 |

**`executeGeneration` 的 `grade` / `realmLv` / `category` 全部由入参决定。**
`normalizeGeneratedTechniqueCandidateForServer`（:833）会在 :845-853 用入参**强制覆盖** LLM 返回值。
roll 只发生在 `requestGeneration`（:155-158），绕开它即可完全指定三要素。

`recoverPendingJobs`（:571）就是范例——启动期不传 `refundItem`、不扣任何道具地批量调 `executeGeneration`。

**致命约束：强依赖外部 LLM，无本地 fallback。**

```
executeGeneration:275 → executeAiTask → callTextModelWithConfig
                     → ai-text-client.ts:6-7  (@anthropic-ai/sdk / openai 真实 HTTP)
```

- 单次超时 60 秒（:271），最多 `maxAttempts = 3`（:260），最坏 **180 秒**
- 模型未配置直接 `NO_MODEL` 失败
- 功法的 name / desc / attrRatio / skills **全部来自 LLM 返回的 JSON**，服务端只做归一化与预算约束
- 现有玩法是 `setImmediate` 异步 + 客户端每秒轮询（最多 120 次）

**所以「踏阵瞬间现场生成多门功法」不可行。** 这是选择「后台预生成功法池」的直接原因。

**生成物是草稿，必须发布才可用**：`insertGeneratedTechnique` 落 `generated_technique` 表（id 形如 `gen_<16hex>`）。
`techniqueTemplates` Map 启动期冻结，AI 功法**不写入其中**；注册表 `tryGetRef` 先查冻结 Map，
未命中再 fallback 到 `generatedStore.getById(id)`，而 store 缓存**只装 `is_published = true` 的行**。
草稿态无法被解析。必须 `publishGeneratedTechnique` + `refreshAfterPublish` 之后才生效。

### 4.8 藏经台（不是「藏书阁」）

全仓**不存在**名为「藏书阁」的对象。功能上最近的是**藏经台 `scripture_platform`**，
它是一个**建筑**（`packages/server/src/runtime/building/building-default-content.ts:56-69`），不是 NPC、不是 landmark。

- **只能存一门功法**：`building-types.ts:163-173` 的 `scriptureTechniqueId` 是单值，不是数组
- 那门功法必须是某个玩家**已练满的自创功法**，由他站在 1 格内手工录入（`transmission.strategy.ts:390-453`）
- **与宗门完全无关**：参悟/录入校验里零 sect / 贡献度检查（`transmission.strategy.ts:455-503`）。
  放置时的 `ownerSectId` 只是归属标记
- 参悟门槛只有三条：建筑 `state === 'active'`、玩家在 1 格内、玩家尚未掌握该功法
- 放置硬门槛只有一条：实例 `meta.persistent === true`（`world-runtime-building.service.ts:46-47`）
- **每个实例构造时都无条件装载含 `scripture_platform` 的默认建筑目录**（`map-instance.runtime.ts:533-534`），
  运行时注册的地图也不例外

**地图 document 没有 `buildings` 字段**，无法在模板里预置建筑。
所以秘境的藏经台必须在实例创建后由服务端直接放置，并写入 `scripture*` 字段 + `markScriptureBuildingDirty`。

### 4.9 boss 掉自创功法书：需要新的授予路径

成品书 = `receiveInventoryItem({ itemId: 'book.custom_technique', learnTechniqueId: 'gen_xxx', ... })`。

- **「固定满层」= 不写 `learnTechniqueMaxLevel`**（`world-runtime-use-item.service.ts:280`
  的 `...(maxLevel < maxTemplateLevel ? { learnTechniqueMaxLevel } : {})`）。写了才是残卷
- `learnTechniqueId` 是**实例级**字段，`book.custom_technique` 模板本身没有它
- 而 drop 系统按**模板 itemId** 掉落，`getMonsterDropItemGrade` 读的也是模板级 `learnTechniqueId`

**因此 boss 掉书不能走 `rollMonsterDrops`**，必须新开一条「击杀 boss → 直接 `receiveInventoryItem`
带 per-instance `learnTechniqueId`」的授予路径。可复用 `dispatchCraftTechniqueBook`(:276-288) 的字段结构，
但跳过它的全部前置（靠台、已掌握、消耗 `mat.technique_fragment`）。

> ⚠️ 若填 `book.custom_technique` 而不带 `learnTechniqueId`，得到的是**空白残卷**——
> 正是 `technique_delete_empty_custom_books` 这个 GM 转换要清理的对象。

## 5. 必须改引擎的三处

| # | 位置 | 改什么 | 为什么绕不过 |
|---|---|---|---|
| 1 | `runtime/instance/tile-recovery-provider.ts` 的 `TileRecoveryConfig` | 单个 `enabled` 拆成 `regenEnabled` / `respawnEnabled` | 见 5.1 |
| 2 | `respawnTicks` 的三份归一化副本 + tick 侧 | 加 sentinel 表达「永不复活」 | 见 5.2 |
| 3 | `shared/src/terrain.ts:182` `calculateTerrainDurability` | 加实例级额外倍率入参 | 见 5.3 |

### 5.1 地形：`enabled: false` 是一刀切

`resolveTileRecoveryProvider(instance)`（`world-runtime-instance-tick-orchestration.service.ts:1037-1044`）
只认 `kind === 'tower'`，命中就返回 `enabled: false` 的 provider。而 `enabled: false` 同时导致：

- destroyed 分支 `continue`（`map-instance.runtime.ts:3517-3519`）→ **不复生** ✅ 我们要的
- damaged 分支 `baseRepairAmount = 0`（`:3568-3571`）→ **1%/息 自然回血也没了** ❌ 我们不要的

单个布尔表达不出「留回血、只关复生」这第三种状态。

> `DungeonTileRecoveryProvider` 这个类写好了但**从来没人 `new` 过**——
> `resolveTileRecoveryProvider` 用的是另一个内联常量 `DUNGEON_NO_RECOVERY_PROVIDER`。

### 5.2 怪物：没有任何值能表达「永不复活」

`respawnTicks` 的归一化在全仓有**三份近乎相同的副本**：

- `content-template-utils.ts:471` `resolveFallbackSpawnRespawnTicks`
- `content-template.repository.ts:1109` 同名副本
- `content-template.repository.ts:930-939` `normalizeMonsterRespawnTicks`（`:535` 调用）

三份全部 `Math.max(1, ...)` 兜底。`0` / 负数 / `undefined` 被钳成 1 或默认 **15**；
`Infinity` 被 `normalizeMonsterRespawnTicks` 的 `Number.isFinite` 守卫堵死，同样回退 15。
全仓**未找到** `noRespawn` / `oneShot` / `neverRespawn` 任何字段。

**现状：秘境里的怪，击杀后必然在 15 秒内满血复活。**

tick 侧递减在 `map-instance.runtime.ts:6316-6321`（`advanceMonsters`），
另有一条降频补偿路径 `performThrottleCatchUp:730-736`。死怪**保留在 `monstersByRuntimeId` 里不删除**
（`alive = false`），每 tick 走轻量分支后 `continue`，不跑 AI。

### 5.3 地形倍率：不能靠篡改 `mapLv` 绕过

`mapLv` 在服务端**只有一个逻辑消费点**——就是地形血量：

```ts
// map-instance.runtime.ts:7495-7498
const mapLv = Number.isFinite(template.source?.mapLv) ? Math.max(1, Math.floor(...)) : 1;
return calculateTerrainDurability(mapLv, profile.multiplier);
```

但它同时经 `world-sync-map-snapshot.service.ts:1161` **原样发给客户端显示**。
把 `mapLv` 篡改成换算值，玩家看到的地图等级就错了。
且 `mapLv` 取整会让 `1.1^(L−1)` 的换算产生 9%~27% 的误差。

所以 `1.1^(L−1)` 必须作为独立的实例级倍率入参传给 `calculateTerrainDurability`。

## 6. 已预留、只等接线的空壳

有人在此之前规划过秘境，但停在了接口层。以下三处**全部零消费者**：

| 位置 | 内容 | 现状 |
|---|---|---|
| `runtime/instance/dungeon-descriptor.ts` | `DungeonDescriptor{type,params}`、`DungeonTemplateFactory.ensureTemplate()`、`RandomCaveDungeonParams{seed,difficulty,biome}`、`TowerTemplateFactory` 范例 | 具名导出全仓零引用。但「descriptor 概念」是活的——被内联对象字面量实现了 |
| `world-runtime-lifecycle.service.ts:699` | 注释：`// 后续秘境类型在此扩展：random_cave、trial 等` | Phase 5 只有 `descriptor.type === 'tower'` 分支 |
| `runtime/instance/tile-recovery-provider.ts` | `DungeonTileRecoveryProvider` 类 | 写好了，从未被 `new` 过 |

**`RandomCaveDungeonParams` 里的 `difficulty` 字段没有任何运行时消费者。**
全仓的 `difficulty` 只存在于功法修炼经验曲线、AI 造功法、以及这个预留字段，
三者互不相关，没有一处影响怪物强度或奖励。**跨系统的 difficulty 概念不存在，秘境等级 L 得自己造。**

正解是新增一个 `RandomCaveTemplateFactory implements DungeonTemplateFactory`，读 `params.seed`，
而不只是加一个 hydrate 分支。

## 7. 实例生命周期与重启恢复

### 7.1 创建

```
registerRuntimeMapTemplate(document)     // 内存注册，不落库
  → createInstance({ instanceId, templateId, kind, persistent, ... })
  → 逐只 addRuntimeMonster(...)           // 怪物必须走这条，见 4.3
  → 逐个放置 scripture_platform 并写 scripture* 字段   // 需新路径，见 4.8
```

`createInstance` 内部的 `createRuntimeMonstersForMap(template.id)` 对内存图**必然返回空**，
所以模板注册时 `monsterSpawns: []`，怪物全靠事后注入。

**同一 `templateId` 的所有实例共享同一个 template 对象引用**（静态地形、landmark 定义、container 掉落配置）。
因此**必须一 seed 一 templateId**，不能复用同一 template 造多个实例，否则宝箱和地形都一样。

### 7.2 销毁

参照通天塔 `cleanupIdleInstances`：无人 + `tick - lastEmptyTick >= idleDestroyTicks`（默认 3600 tick）
→ flush 落盘 → `meta.status = 'destroyed'` → `deleteInstanceRuntime` + 清 tickProgress/loot/eventBus/formation
→ `markCatalogDestroyed`。

### 7.3 重启恢复（关键约束）

**运行时注册的模板不落库。** 重启后 `templateRepository` 只从磁盘 JSON 重建；
catalog 恢复时若 `!templateRepository.has(templateId)`（`world-runtime-lifecycle.service.ts:280`）
→ `markMissingTemplateCatalogEntry` → 实例标 `template_missing` 并**跳过创建**。

通天塔靠 `restoreCatalogTowerTemplate`（`:257`）在建实例前**确定性重建**模板：
从 `template_id` / `instance_id` 反解 layer，再 `ensureLayerTemplate(layer)` 全量推导。

**所以秘境要活过重启，必须提供确定性重建能力。** 而这正是 procgen 的天性——
`(seed, L)` 是完整的重建参数，写进 `dungeonDescriptor.params` 即可：

```ts
// world-runtime-persistence-state.service.ts:431-453 已支持
dungeonDescriptor = { type: 'random_cave', params: { seed, level: L } };
```

`DungeonDescriptor.params` 是 `unknown`，无 schema 约束。checkpoint 会完整持久化并在
`hydrateInstanceFromCheckpoint` 交回。

> 两个补充事实：
> - tower 恢复成功后还会 `primeLayerInstanceCache`（`:260-262`）预热实例缓存。秘境可能同样需要
> - 被标 `template_missing` 的实例并非死透——下次恢复若模板已能重建，`runtime_status` 会被复位为 `'running'`（`:297-299`）。
>   只要提供了确定性重建钩子，秘境可以自愈

> ⚠️ 现有 checkpoint 快照的 descriptor 构造前置条件是
> `instance?.tongtianTowerState && instance?.meta?.kind === 'tower'`（`:434`）。
> 新秘境类型必须自建 dungeonState 或改写此段。

> ⚠️ `instance.meta` 是 28 个字段的**写死字面量**（`map-instance.runtime.ts:496-525`），
> `request` 里未被显式读取的键会被静默丢弃。**没有「自由元数据」通道**，秘境等级 L 只能走 `dungeonDescriptor.params`。

## 8. 待决清单

以下尚未敲定，需继续讨论：

1. **区域拓扑的数据结构**。骨架图（入口→战斗房→宝库→boss→出口）用什么表示？
   区域类型有哪些（开放地貌 / 迷宫 / 地牢 / 走廊 / 宝库 / boss 房）？
2. **区域数随面积的缩放口径**。当前 `ProcgenBuildingSpec.count` 是绝对数 `[1,2]`，
   64² 到 256² 恒为 2 栋。需要换成按面积/按拓扑节点数的口径。
3. **怪物撒点从「房屋副产物」拆成独立系统**。当前 `ProcgenContentAnchor{x,y,kind:'chest'|'monster'}`
   只在房屋内部产生，需要扩展成能覆盖全图、能翻译成怪物注入清单的完整内容描述。
4. **秘境等级 L 从哪来**。玩家境界？传送阵配置？地图组？
5. **杂兵/精英怪的 biome → monsterId 池映射表**。引擎无地形门控，必须生成器自建。
6. **功法池的分档与容量**。按 grade × realmLv 分多少档？每档存多少门？池空时的降级策略？
7. **秘境实例是否 persistent**。藏经台放置要求 `meta.persistent === true`；
   但 persistent 实例会进 catalog、参与重启恢复、占持久化开销。
8. **草药按地形分布的映射表**。同 5，引擎无地形门控（`resource-nodes.json` 无 terrain/biome 键）。
