# 密室建筑与实例级异速调度实现计划

> 状态说明（2026-07-17）：本文主体记录 2026-07-12 的首版“持续设速、逐息耗油”实现，仅作为历史设计记录。现行玩法已简化为开启者按倍率、实际配置容量、空间档位和整小时数一次付费；`1x` 常驻开放且无需开启时段，更高倍率开启后整间密室锁定到统一截止时间，期间禁止续时、改速或提前关闭。当前权威规则以 `docs/mechanics/building-env/23-building-system.md` 与 `docs/mechanics/core-loop/01-tick-scheduling.md` 为准。

## 1. 目标与已确认规则

本计划一次性实现可建造、可持久化、可进入、可管理的密室建筑，并根治当前“任一实例加速会抬高全服调度频率”的耦合问题。

已确认玩法规则：

- 密室是可建造的地面设施，建成后对应一个唯一、持久化的独立地图实例。
- 所有玩家都可以进入，不做创建者或关系权限限制。
- 首版同一密室最多容纳 1 人，但容量判断必须收敛到独立准入策略；后续改为多人时不得重做传送、协议或实例结构。
- 玩家不可重叠仍由现有服务端 occupancy 权威保证，不为密室另写碰撞规则。
- 创建者可在建筑外打开独立控制台，修改名称、投入灵石、调整时间流速和地图大小。
- 时间流速支持整数 `1x` 至 `10x`。`1x` 是无燃料时的安全基准速度；高于 `1x` 才消耗灵石。
- 速度越高，每现实秒执行的逻辑息越多，且每个加速逻辑息的单位成本也更高，因此总消耗随速度超线性增长。
- 燃料按实际获准并执行的加速逻辑息扣除；被公平性限流、积压丢弃或未执行的逻辑息不得收费。
- 燃料耗尽、持久化不可用或运行缓冲补充失败时，实例自动回落到 `1x`，不能停止在无法离开的状态。
- 密室尺寸首版提供离散档位，修改尺寸只允许在密室无人时执行；不做带玩家、建筑、掉落或战斗对象的在线裁切迁移。
- 建筑拆除前必须确认密室无人；有在线或离线保留玩家时拒绝拆除，避免孤儿实例和玩家被困。

## 2. 当前链路与问题结论

### 2.1 当前异速数据流

当前链路为：

`instance.tickSpeed` → `WorldTickService.resolveEffectiveTickIntervalMs()` 扫描全部实例取最高速度 → 全局 `setTimeout` 提频 → `advanceFrame(actualElapsedMs)` 扫描全部实例 → 全连接玩家同步 → 全事件总线清空。

实例自身通过 `WorldRuntimeTickProgressService` 累计小数进度，这能算出不同实例应走多少逻辑息，但驱动、命令物化、同步和收尾仍是全局的。少量 `10x` 实例会因此把以下工作从 `1Hz` 放大到 `10Hz`：

- 全实例扫描和死亡玩家安全网扫描；
- 全连接玩家的自动用药、自动战斗与 pending command 派发；
- 全连接玩家的视图构建、协议 diff、辅助状态和事件消费；
- 通天塔全局清理等世界级维护；
- 容器翻找推进。当前容器搜索每个调度帧直接 `remainingTicks -= 1`，会让普通地图被其他高倍速地图错误加速。

### 2.2 密室状态数据流

目标链路为：

建筑完成并交互 → 按 `sourceInstanceId + buildingId` 查找或创建密室状态 → 注册该密室独有的运行时地图模板 → 创建/恢复持久实例目录与实例 checkpoint → 通过玩家命令队列执行准入校验和跨实例传送 → 密室实例按自己的 deadline 推进 → 仅同步该实例玩家。

控制台链路为：

客户端提交低频结构化意图 → 服务端校验会话、距离、建筑状态和创建者身份 → 在领域服务中串行修改 → 数据库真源提交 → 更新实例运行态和调度 deadline → 返回最新详情视图。

灵石投入链路为：

玩家背包快照预演 → 玩家资产串行区 → durable operation 同一数据库事务内替换玩家背包行并增加密室燃料单位 → 提交后替换玩家运行态背包 → 返回密室详情和玩家增量。

## 3. 架构边界

### 3.1 shared 与内容配置

- `BuildingDef.timeChamber` 只描述内容能力和限制：默认容量、最大倍速、每枚灵石燃料单位、允许尺寸。
- shared 新增密室协议视图和请求类型，不承载服务端资产裁定。
- 建筑目录新增 `time_chamber`；启动期编译并校验所有密室配置，运行期不解析 schema。

### 3.2 服务端运行时

- `TimeChamberRuntimeService` 是密室领域真源的运行时入口，负责状态缓存、模板注册、实例确保、准入、控制台操作、燃料授权和拆除前检查。
- `TimeChamberAdmissionPolicy` 只负责容量判断。首版返回容量 `1`，未来扩容只替换状态/配置，不改传送主链。
- 位置改变仍通过通用 `WorldRuntimeTransferService`；socket handler 不直接改坐标。
- 密室进入/离开进入现有玩家 pending command 队列，在来源实例到期批次内执行并二次校验容量。
- 密室内部不复制玩家、不使用第二套战斗或成长状态；地图加速等价于该实例完整逻辑息加速。

### 3.3 调度器

新增 `WorldRuntimeInstanceScheduleService`，只维护内存 deadline，不注册“一实例一 SchedulerManager task”，以满足单服 10000 实例口径。

调度结构：

- 使用单调时钟 `performance.now()`。
- 普通/低速实例和加速实例使用两个最小堆；每个实例只有一个当前 generation，旧堆节点惰性失效。
- 普通实例到期批次永远先于加速债务，避免高倍速 backlog 饿死 `1x` 地图。
- 稳态 `nextDueAt` 基于上一次 deadline 递推，避免按完成时间重排造成长期漂移；主动改速时从当前单调时钟按新间隔重新起算，避免降速后多走一息。
- 单批限制实例数和单实例追赶息数；超出上限的历史债务计数后丢弃，并从当前时间重同步 deadline，不做无界 while catch-up，也不收取对应燃料。
- 队列不持久化。启动时由已恢复实例的 `tickSpeed / paused` checkpoint 重建。
- 冷启动重建时按稳定 `instanceId` 计算首个 deadline 相位，将大量同速实例确定性错峰到各自间隔内；后续仍按固定间隔递推，避免 10000 个实例在启动后一刻同时到期。
- 创建、恢复、销毁、fence、暂停和改速统一通知调度服务；弹出节点时仍复核实例引用和 lease。

`WorldTickService` 每次只取已到期实例计划，调用实例级编排并仅同步相关玩家。没有实例到期时仍以 `1Hz` 唤醒世界维护时钟；有错峰 deadline 时也按当前 `10x` 上限把全局 dispatcher 帧起始频率限制为最多 `10Hz`，同一 `100ms` 量子内到期的实例合批处理，不能退化为 `5ms` 全局轮询。单批上限为 `2048` 个实例，可覆盖 10000 个 `1x` 实例在十个量子内各推进一次并保留约两倍分布偏斜余量。

### 3.4 实例编排与副作用

`advanceFrame` 接受明确的 due plans，不再为高频帧遍历所有实例计算进度。以下链路改为实例范围：

- 寻路意图物化；
- 自动用药与自动战斗；
- pending player command 派发；
- 实例 tick、地块、阵法、玩家成长、技能和 craft job；
- 容器搜索；
- quest 刷新；
- 玩家同步与实例事件清理。

世界时钟、GM/system command、死亡恢复安全网和跨实例清理按真实 `1Hz` 世界节拍运行。死亡增量集合可以在到期批次处理，但只有世界节拍允许触发全量安全网。

跨实例传送产生的玩家必须加入本批同步集合；目标实例本身不因接收玩家而被迫额外走一息。

### 3.5 网络同步

- `WorldSyncService` 增加按实例/玩家集合刷新入口，复用现有单玩家 envelope 和 aux 逻辑。
- 只枚举 `WorldSessionService` 已维护的实例玩家索引，不在每个高频批次扫描全部 binding。
- 玩家 delta 在组包时消费玩家事件；当本批该实例玩家同步完成后，只清理相应实例表现队列。
- 禁止高频批次调用全局 `RuntimeEventBusService.flushTick()`，否则会清掉尚未同步的普通地图事件。
- 密室控制台使用低频独立事件：详情、投入燃料、改速、改名、改尺寸。回包只含控制台所需字段。

## 4. 持久化设计

新增表 `instance_time_chamber_state`：

| 字段 | 含义 |
| --- | --- |
| `source_instance_id` + `building_id` | 外部建筑唯一键 |
| `chamber_instance_id` | 密室持久实例唯一键 |
| `template_id` | 该密室独有的运行时模板 ID |
| `owner_player_id` | 控制台管理者 |
| `display_name` | 自定义名称回读兜底 |
| `size_tier` | `small / medium / large` |
| `capacity` | 当前准入容量，首版为 1 |
| `configured_speed` | 当前目标倍速，范围 1 至 10 |
| `fuel_units` | 数据库中尚未装载到运行时的可用燃料单位 |
| `revision` | 控制台乐观版本和详情刷新版本 |
| `created_at / updated_at` | 审计时间 |

燃料采用整数单位，避免浮点资产误差：

- 每枚灵石转换为内容配置给出的固定 fuel units。
- 速度 `s` 每执行一个加速逻辑息消耗 `s - 1` units；现实每秒约执行 `s` 息，因此总速率为 `s × (s - 1)` units/秒。
- 调度热路径只消耗已预留到内存的短时运行缓冲，不做数据库 IO。
- 运行缓冲由数据库原子扣减后才能使用；进程崩溃或实例切换节点时宁可损失最多一个有界短缓冲，也绝不重复生成燃料。缓冲大小固定受限，补充失败记录结构化日志并立即降级。
- 详情显示数据库可用量与当前进程缓冲之和，并按当前速度给出估算剩余时间。

实例自身的 `tick / tickSpeed / paused` 继续由现有 time checkpoint 持久化；密室表是玩法配置和燃料真源。启动恢复顺序为：

1. 初始化密室表并加载状态；
2. 按状态注册所有动态模板；
3. 恢复 instance catalog 与实例 checkpoint；
4. 恢复玩家位置；
5. 将密室状态重新应用到实例并重建 deadline 队列；
6. 最后开放 tick 和流量。

## 5. 地图与尺寸

每个密室使用独有模板 ID，模板由状态中的尺寸档位确定：

- `small`：9 × 9；
- `medium`：15 × 15；
- `large`：21 × 21。

模板为无怪物、无容器、无资源点、全域安全区的封闭地面，出生点在中心。退出通过密室内部上下文动作完成，不依赖静态 reciprocal portal。

改尺寸时必须同时满足：

- 操作者是创建者并位于外部建筑附近；
- 密室实例中没有任何玩家；
- 目标档位在建筑配置允许集合中；
- 实例 lease 本地可写。

满足条件后注册新模板对象，并用“空实例模板替换”入口重建 tile plane、occupancy、AOI 和路径缓存；不迁移任何动态对象。状态与实例 time checkpoint 随后立即落库。

## 6. 建筑生命周期

- 上下文动作只在建筑 `active` 且距离不超过 1 格时出现。
- 所有人看到“进入密室”；只有创建者额外看到“密室控制台”。
- 密室内玩家看到“离开密室”。
- 初次交互幂等创建状态、模板和实例；重复请求返回同一实例。
- 改名同时更新建筑快照和密室状态，AOI 只 patch 受影响建筑。
- 主动拆除先调用密室领域检查：有人则拒绝；无人则将实例降为 `1x`、标记停止/销毁并删除密室状态，之后才允许删除建筑。
- 启动禁建区自动清理若命中密室建筑，也必须走同一领域清理规则；无法安全清理时保留建筑并记录错误，不能留下无法追溯的实例。

## 7. 客户端控制台

控制台使用共享 detail modal 宿主，局部 patch 当前详情，不重建游戏主面板。内容包括：

- 名称与当前管理权限；
- 当前尺寸、容量和占用；
- 当前/目标倍速；
- 剩余燃料、当前消耗率和估算时长；
- 灵石投入数量；
- `1x` 至 `10x` 速度选择；
- `small / medium / large` 尺寸选择。

客户端只做输入范围提示和显示，所有权限、余额、占用、尺寸及速度合法性由服务端复核。UI 同时覆盖浅色、深色和手机弹层高度/触控命中。

## 8. 安全性与降级

- 数据库或 durable operation 不可用：禁止投入燃料、改速和首次创建持久密室；已有玩家仍可离开，实例强制 `1x`。
- 燃料不足：服务端回落 `1x` 并发结构化通知；客户端不能自行维持高倍速显示。
- 调度超载：普通 deadline 优先；加速实例追赶有上限，超额欠债直接丢弃并重新对齐当前时间，不影响正常地图 `1Hz`，也不会消耗燃料。
- lease 暂时不可写：该实例逻辑时间暂停，deadline 延后重试并保留索引；实例被销毁或卸载后才永久移出调度器。
- 控制台重复提交：请求携带 `requestId`，资产投入由 durable operation 幂等；其他修改使用状态 revision 和领域串行队列。
- 两名玩家同时进入容量 1 密室：命令在主线程顺序执行，每次连接目标前重新读取 occupancy/capacity，只有第一名成功。
- 调整尺寸与进入竞争：二者使用同一密室串行区；进入成功后尺寸修改必然因 occupied 被拒绝。

## 9. 实施顺序

1. shared 类型、协议、建筑配置 schema 与内容目录。
2. deadline 调度服务、实例范围编排、命令/自动行为/容器搜索和同步收口。
3. 密室持久化表、动态模板、准入策略、燃料 durable source mutation 和恢复链。
4. 建筑上下文动作、进入/离开命令、拆除保护和统一改速入口。
5. 客户端控制台、网络 sender/binding、局部更新和响应式样式。
6. mechanics 文档、调度与密室 focused smoke、持久化自动清理。
7. 执行 shared/protocol、server、client 最小门禁并修复回归。

## 10. 验证标准

必须至少证明：

- 一个 `10x` 密室在一秒内推进约 10 个实例息，同时普通实例只推进 1 息。
- 高频批次不调用普通实例的自动行为、pending command、容器搜索或玩家同步。
- 普通实例 deadline 在加速 backlog 下仍优先执行，单批 catch-up 上限生效。
- 密室燃料只按实际执行的加速息扣除，耗尽后回落 `1x`。
- 灵石投入在 durable 事务失败时玩家背包与密室燃料均不改变；重复 operation 不重复扣款或加油。
- 任意玩家可以进入；容量为 1 时第二名被服务端拒绝；离开后下一名可进入。
- 改尺寸在空密室成功，有人时失败；改名、速度、尺寸和燃料在重启后保持。
- 拆除有人的密室被拒绝，无人密室能清理实例和状态后再拆除。
- 首包、跨图、断线重连和恢复后的玩家只收到所属实例必要同步。

最小门禁：

```bash
pnpm build:shared

pnpm verify:quick
pnpm verify:client
```

## 11. 实施结果与验证记录

已按本计划完成 shared 契约、建筑内容、密室领域持久化、动态地图模板、准入与传送、燃料 durable operation、实例 deadline 调度、实例范围 tick/同步、客户端控制台及机制文档。首版容量固定为 1，但准入策略、状态字段、协议视图和占用计数均保留可变容量接口。灵石投入若遇到 `COMMIT` 已发送但回包不确定，会沿用同一 `operationId` 回读并幂等重放，只有收敛到已提交后才更新运行态背包。

最终调度不再根据全服最高倍速抬高全量帧频：每个实例独立登记 deadline；普通实例优先于加速积压；冷启动按实例 ID 错峰；每实例单批最多补 4 息；高频批次只运行并同步到期实例。密室燃料热路径只消费数据库预留的有界内存缓冲，失败或耗尽自动回落 `1x`。
