# 无限秘境开发计划

> 状态：待开始
>
> 制定日期：2026-07-13
>
> 目标环境：8 核 CPU、16GB 内存、30Mbps 出口、5000 并发玩家、10000 地图实例
>
> 首发运行口径：预计 300～500 同时在线；5000 在线仍作为架构与容量硬门槛，不作为可以忽略的远期目标。

## 1. 结论与实施决策

无限秘境可以做，但不能把 tools/procgen-demo 的 InfiniteWorld 直接接进 MapInstanceRuntime。

生产实现采用以下形态：

1. 一个无限秘境仍是一个逻辑地图实例、一个权威 tick 域，不把每个 chunk 建成独立地图实例。
2. MapInstanceRuntime 继续承载玩家、战斗、怪物、交互与命令编排；地图空间存储抽成可替换策略：
   - 有界地图继续使用现有稠密/全模板后端。
   - 无限秘境使用分块后端，只保留玩家附近、寻路窗口和待刷盘 chunk。
3. tools 中的连续噪声、overscan、确定性结构散布可以复用算法思想；演示缓存、逐格 Tile 对象和主线程生成不能进入生产链路。
4. 地图历史只持久化 seed、generatorVersion、chunk 元数据和稀疏变化，不保存全部基础地块。
5. 不提供小地图，不记录无限秘境的客户端地图记忆，不允许全图或超远距离寻路。
6. 首发建议将无限秘境内每息实际移动步数硬限制为 1，玩家寻路目标曼哈顿距离限制为 48 格；两者均由服务端实例规则控制，客户端只能提前提示，不能放宽。
7. 现有有界秘境继续负责“入口→战斗→宝库→boss→出口”的结构化关卡；无限秘境是持续探索玩法，不替代现有秘境。

在正确分块后，探索历史达到 1024×256 格只意味着约 132 个 48×48 chunk 曾被访问，不应让 262144 个地块常驻内存，也不应让 tick、寻路、渲染或刷盘扫描这 262144 格。

## 2. 已确认需求与首发假设

### 2.1 已确认需求

- 无限秘境允许长时间持续探索。
- 不显示小地图。
- 不提供超远距离寻路。
- 寻路只需要局部窗口。
- 可以强制降低移动推进速度。
- 实际同时在线预计为 300～500，系统仍需在 5000 在线口径下有明确容量证明。

### 2.2 推荐首发默认值

| 项目 | 推荐值 | 说明 |
|---|---:|---|
| instance kind | infinite_realm | 与 tower、sect 和普通有界地图区分 |
| persistent policy | persistent | 允许跨重启和跨天探索 |
| chunkSize | 48 | 与当前生成器一致；一旦随 generatorVersion 发布后不可原地修改 |
| 视野半径 | 10 格 | 复用当前 AOI/FOV 口径 |
| 最大寻路目标距离 | 48 格曼哈顿距离 | 约一个生成 chunk，明显低于当前全局 96 格 |
| 最大寻路展开节点 | 4096 | 只允许局部窗口，不允许退化为整图 |
| 每息最大实际移动步数 | 1 | 限制跨 chunk 速度、生成尖峰和网络增量 |
| 客户端保留范围 | 当前可见 chunk + 1 圈保护环 | 超出后按引用和 LRU 淘汰 |
| 小地图 | 强制关闭 | mapMeta.hideMinimap=true，且不写客户端地图记忆 |
| PVP | 首发关闭 | 与流式地图底座解耦，后续单独评估 |
| 玩家建造、房间、风水 | 首发关闭 | 避免把全图拓扑和房间重算带入无限空间 |
| 地块破坏 | 底座支持稀疏 delta，首发灰度前默认关闭 | 通过持久化与恢复门禁后再开启 |

上述数值必须进入共享配置 schema，并在配置编辑器、导入期和服务端启动期校验；不得散落成 socket handler 或客户端常量。

### 2.3 空间语义

- 世界格坐标使用有界的 signed Int32 语义，首发安全范围限制在正负 2 的 30 次方减 1 以内，为半径运算和相邻格计算保留溢出余量。
- “无限”指玩家在正常运营周期内无法到达边缘，不承诺数学意义上的无限整数平面。
- 原点附近必须生成稳定、安全、可行走的出生区域和返回出口。
- 无限秘境不设计唯一的世界尽头或全局最终 boss；局部事件、区域首领和奖励锚点由内容层按 chunk 或宏区生成。

## 3. 当前实现事实与问题基线

### 3.1 已有能力

| 链路 | 当前事实 | 可复用部分 |
|---|---|---|
| 生成器 | packages/shared/src/procgen/procgen-chunk.ts 按 seed、cx、cy 确定性生成，使用世界坐标连续噪声和 overscan | 连续噪声、跨块无缝、确定性规则 |
| 演示缓存 | tools/procgen-demo/src/infinite-world.ts 支持按需生成和远处淘汰 | 只作为行为原型，不作为生产运行时 |
| AOI/FOV | 服务端按视野半径 10 做 shadowcasting，只同步可见地块和对象 | 视野规则、AOI 增量原则 |
| 网络 | 首次进入发送 MapStatic 可见窗口，移动后通过 WorldDelta 发送 tile patch | 分层同步框架 |
| 客户端渲染 | Pixi 渲染器按 16×16 可见渲染块创建与回收容器 | 视口裁剪、局部重建、渲染块缓存 |
| 实例持久化 | instance_catalog、ownershipEpoch、leaseToken、分域 flush 和恢复水位已经存在 | 实例目录、租约与刷盘围栏 |

### 3.2 不能直接复用的部分

| 问题 | 原因 | 后果 |
|---|---|---|
| RuntimeTilePlane.fromTemplate 全量激活 width×height | 当前有界地图以整张模板为真源 | 地图面积直接放大初始化时间和内存 |
| occupancy、roomId、aura、baseAura 等按全图 cell capacity 分配 | MapInstanceRuntime 仍以全局 cellIndex 为核心 | 每个大实例约几十 MiB，多个秘境线性相乘 |
| cell capacity 使用 2 次幂扩容 | 超过容量时整组 TypedArray 复制 | 262145 格会触发 262144→524288 的明显停顿和内存跃迁 |
| AsyncPathfindingService 按 width×height 构建静态网格 | 目标距离上限只限制请求，不限制网格构造 | 即使只走几格，首次寻路仍可能扫描和分配整图 |
| buildRuntimeTilePersistenceEntries 扫描全部激活 cell | 有界模板通过逐格比较找动态覆盖 | 无限基础地块会被误当成运行时地块，刷盘退化为全历史扫描 |
| 房间/风水初始化扫描整图 | 构造器无条件重建静态房间拓扑 | 无限秘境即使禁建造也支付全图成本 |
| 客户端 tileCache 和 renderTileCache 保留会话历史 | hideMinimap 只阻止写长期地图记忆 | 长途探索仍会在当前会话积累 Tile 对象和克隆对象 |
| 当前生成器输出字符串数组和逐格对象 | 面向 demo 与冷路径可视化 | 不适合作为服务端活跃 chunk 的紧凑存储 |
| 当前五个无限主题是 TS 硬编码 | 未进入内容 schema 和编辑器契约 | 无法做发布校验、版本冻结和运营配置 |
| 当前无限生成器没有生产消费者 | 全仓除 tools 和 shared 定义外没有接入点 | 不能把 demo 的“能走”理解为服务端已经具备流式能力 |

### 3.3 2026-07-13 本机诊断基线

以下数据只用于识别增长模型，不是正式容量承诺：

| 场景 | 结果 |
|---|---:|
| 1024×256、262144 格 MapInstanceRuntime 初始化 | 约 498ms |
| 同一实例服务端 RSS 增量 | 约 34MiB |
| 同一实例 ArrayBuffer 占用 | 约 22.8MiB |
| buildRuntimeTilePersistenceEntries 全量扫描 | 约 64ms |
| rebuildBuildingRoomFengShuiState 全量扫描 | 约 42ms |
| 当前整图网格首次局部寻路 | 约 85ms |
| 激活第 262145 格触发容量翻倍 | 约 61ms，RSS 额外增加约 17MiB |
| 客户端缓存 262144 个 Tile 对象 | 约 47MiB heap |
| 再叠加 renderTileCache 克隆 | 合计约 88MiB heap |
| demo 长途视口样例 | 121 个已载 chunk、约 27.9 万 Tile、约 212MB JS heap |
| demo 首次跨 chunk 样例 | 约 800ms 主线程停顿 |

因此，现架构下“单个 1024×256 地图能运行”不等于“无限秘境可长期运行”。真正风险是多个实例相乘、容量翻倍停顿、会话历史缓存和全图冷路径扫描。

## 4. 目标与非目标

### 4.1 功能目标

- 相同 seed、generatorVersion、themeId 和 chunk 坐标必须生成相同基础结果。
- 玩家可以跨 chunk 连续移动，跨块地形、结构和视觉边缘无缝。
- 原点出生区域必定可行走，并与至少一个稳定探索出口及返回传送点连通。
- chunk 可按玩家视野、路径和实体需要加载，也可在无人引用后安全休眠。
- 实例和 chunk 能跨进程重启恢复，不重复生成奖励，不复活已经结算的一次性内容。
- 客户端只持有有限窗口，不因探索时长增长。
- 所有位置、占位、战斗、掉落、交互和地块变化仍由服务端权威裁定。

### 4.2 性能目标

- 服务端内存、tick、寻路、同步和刷盘复杂度只与活跃 chunk、活跃实体和当前视野相关，不与历史探索面积相关。
- 静态基础地貌永不进入 tick 遍历。
- 寻路不得构建整张无限地图网格，不得在失败时回退到当前整图 AsyncPathfindingService。
- 刷盘不得扫描全部历史 chunk 或全部基础地块。
- 客户端不得用字符串坐标 Map 和逐格 Tile 克隆保存全部探索历史。
- chunk 生成不得阻塞 tick，不得占满现有 Encoding Worker Pool。

### 4.3 非目标

- 不替换当前有界秘境、通天塔、宗门地图和普通模板地图。
- 不实现全局小地图、探索历史地图、自动跨区导航或超远距离 A*。
- 不把 seed、隐藏结构锚点或完整 chunk 发给客户端做权威生成。
- 不把每个 chunk 建成 MapInstanceRuntime。
- 不在首发阶段支持玩家建造、房间识别和风水。
- 不在性能证据出现前引入 Rust。
- 不在 tick 内执行数据库 I/O、JSON 编解码、配置解析或 chunk 生成。
- 不为了“无限”使用超出安全整数或 signed Int32 口径的坐标。

## 5. 目标架构

~~~text
配置编辑器 / 内容目录
        │ 启动期校验并编译
        ▼
shared 版本化生成契约 ────── tools 预览器
        │
        ▼
专用 Procgen Worker Pool
        │ 只返回确定性 TypedArray + 锚点 + baseHash
        ▼
InfiniteRealmChunkManager
        │
        ├── ChunkedMapSpatialStore：地块、占位、资源、局部索引
        ├── MapInstanceRuntime：玩家、战斗、怪物、交互、tick 编排
        ├── AOI/FOV/局部寻路
        └── dirty chunk 快照
                 │
                 ▼
        flush staging / chunk 分域持久化

服务端可见窗口 ── MapStatic / WorldDelta ── 客户端有界 ChunkTileCache
                                              │
                                              ▼
                                      现有 Pixi 分块渲染器
~~~

### 5.1 shared 边界

新增版本化纯类型和纯规则，建议集中在 packages/shared/src/procgen 与 shared 协议类型中：

- InfiniteRealmDescriptor
  - seed
  - generatorVersion
  - themeId
  - rulesetVersion
  - chunkSize
  - coordinateLimit
  - realmLevel
  - contentSetId
  - movementPolicy
- MapSpatialExtent
  - bounded：沿用 width、height
  - streamed：携带 chunkSize、coordinateLimit，不把 width、height 当世界边界
- ChunkCoord、ChunkLocalIndex、ChunkRevision、ChunkBaseHash。
- CompiledInfiniteWorldSpec：配置在启动期编译为数字句柄和不可变查表结构。
- GeneratedChunkBase：
  - terrain、surface、structure、flags 使用 TypedArray。
  - semanticAnchors 使用稳定 ID 和紧凑记录。
  - 不创建 Tile 对象，不保存字符串坐标 key。

generatorVersion 是存档契约，不是展示版本。已经创建的世界必须始终调用对应版本的生成器；新增算法发布为新版本，不允许用新算法静默重算旧世界。

### 5.2 服务端空间后端

不复制一套战斗运行时。先从 MapInstanceRuntime 抽出最小 MapSpatialStore 接口，再提供两种实现：

| 实现 | 使用范围 | 说明 |
|---|---|---|
| BoundedMapSpatialStore | 当前所有有界地图 | 封装现有 RuntimeTilePlane、全图数组和 cellIndex 语义，行为保持不变 |
| ChunkedMapSpatialStore | infinite_realm | 只管理活跃 chunk；所有 cell handle 仅在 chunk 生命周期内有效 |

建议接口只覆盖真实空间职责：

- resolveCell(x, y)
- isLoaded(x, y)
- readStaticLayers(x, y)
- readTraversalCost(x, y)
- read/set occupancy
- read/write sparse tile delta
- enumerateLocalRect 或 enumerateLocalRadius
- acquire/release chunk lease
- snapshotDirtyChunks

业务对象不得持久化进程内 cell handle。怪物、容器、地面物品、临时地块和玩家位置一律以世界坐标或 chunk 坐标加 localIndex 作为稳定身份。

### 5.3 InfiniteRealmChunkManager

每个无限秘境实例持有一个 chunk manager，但休眠实例不保留任何 chunk。chunk 状态机如下：

~~~text
ABSENT
  └─ 请求加载 → GENERATING / LOADING
                    ├─ 失败 → FAILED
                    └─ 成功 → HYDRATING
                                  └─ 校验并叠加 delta → ACTIVE
ACTIVE
  └─ 引用归零并过宽限期 → QUIESCING
                                  ├─ 新引用到达 → ACTIVE
                                  └─ 有脏数据 → STAGING / FLUSHING
                                                   ├─ 失败 → ACTIVE_DIRTY
                                                   └─ 成功 → HIBERNATED
                                  └─ 无脏数据 → HIBERNATED
~~~

chunk lease 至少区分：

- player-view：玩家视野或下一步移动需要。
- path-window：局部寻路期间需要。
- entity-runtime：活跃怪物、容器、掉落或临时对象需要。
- operation：战斗、交互、传送或脚本正在提交。
- flush：正在构造或提交不可变刷盘快照。

引用计数归零不立即销毁，使用短宽限期吸收玩家在 chunk 边界来回移动。任何 dirty chunk 在刷盘或 durable staging 失败时必须留在内存，并触发生成反压；禁止为了释放内存丢弃未落盘状态。

### 5.4 专用生成 Worker

新增有界 Procgen Worker Pool，不复用 Encoding Worker Pool，避免地形生成挤占 AOI 编码和寻路：

- 输入只包含 descriptor、chunk 坐标和启动期编译的只读 spec。
- 输出只包含 TypedArray、semanticAnchors、baseHash 和验证摘要。
- Worker 不持有 socket、MapInstanceRuntime、数据库连接或权威状态。
- 队列有全局上限、实例公平轮转、超时、取消和观测指标。
- 生成结果在 tick 外返回；主线程只在受控预算内完成校验和激活。
- 玩家即将接近边界时预取相邻 chunk。若目标 chunk 尚未就绪，移动意图短暂等待或返回结构化“区域生成中”，不得在 tick 内同步生成。

### 5.5 可达性与内容锚点

当前连续噪声只能保证视觉无缝，不能保证全局连通，且部分主题的原点可能是阻挡地形。生产 V1 必须增加可达性合同：

- 原点安全区在所有 seed 下可行走。
- 返回传送点和出生点使用稳定坐标及稳定 ID。
- 每个宏区通过确定性边界门位或道路骨架与相邻宏区协商连接，边界结果只依赖 seed、generatorVersion 和宏区坐标。
- 结构、资源、怪物和容器先生成 semantic anchor，再由服务端内容翻译器注入运行态。
- 生成后校验当前 chunk 和必要 overscan 邻域；失败时该 chunk 不激活，不用墙、空地或新 seed 静默替代。
- 不承诺整张无限平面只有一个连通分量，但必须保证出生探索骨架和跨宏区主通路连续。

### 5.6 局部寻路

新增 StreamedPathfindingWindow，不能只把现有 PATHFINDING_PLAYER_MAX_TARGET_DISTANCE 从 96 调小：

1. 接收玩家位置和目标位置。
2. 先校验实例规则的最大曼哈顿距离，首发为 48。
3. 取起点与目标包围盒，并增加固定绕障 margin。
4. 只从已激活 chunk 复制局部 walkable、traversalCost 和动态阻挡。
5. 窗口尺寸和节点数有硬上限，首发最大展开 4096。
6. 缺失 chunk 视为 unknown，不视为可走；可触发受控预取，但本次寻路不得穿越未知区域。
7. repath 使用同一局部合同，不允许退回整图网格。
8. 客户端预览只使用已知地块；超距或穿过未知地块时不画虚假完整路径。

局部窗口提交可以继续复用 findBoundedPath 的纯算法，但不得复用 AsyncPathfindingService 当前的整实例 grid cache。

### 5.7 移动、占位与 tick

- 每息最大移动步数由实例 movementPolicy 强制裁剪，客户端 maxSteps 不能扩大。
- movePoints 仍按现有地形代价结算；实例步数上限只限制本息实际推进，不篡改全局移动公式。
- 跨 chunk 移动在同一实例 tick 内完成源占位释放和目标占位写入，目标 chunk 未激活时整步不提交。
- chunk 内 occupancy 使用 Uint32Array；跨 chunk 实体索引使用嵌套数字 Map 或稳定句柄，不在热路径拼接坐标字符串。
- tick 只遍历 active chunk 的活跃实体、dirty 集合和到期队列；静态基础地块不进入 tick。
- 休眠对象把倒计时保存为绝对 worldTick 或明确的 resumeAtTick。恢复时按每种机制的规则补偿，不能简单把空实例跳过的所有副作用一笔带过。
- 一次性怪物或容器必须保存已结算状态；可复生内容保存绝对到期时间，不要求 chunk 离线期间每息递减。

### 5.8 持久化模型

无限秘境不能把现有 instance_tile_cell 当基础地貌表使用。建议增加显式真源：

#### instance_infinite_realm_descriptor

- instance_id
- seed
- generator_version
- theme_id
- ruleset_version
- chunk_size
- coordinate_limit
- realm_level
- content_set_id
- config_revision
- created_at / updated_at

该表在创建 instance_catalog 记录时同一受控操作链写入。恢复顺序必须先读 descriptor，再创建无限实例 shell；现有 checkpoint 中的 dungeonDescriptor 只能作为恢复校验或兼容迁移输入，不能继续作为唯一前置真源。

#### instance_infinite_chunk_state

- instance_id
- chunk_x / chunk_y
- base_hash
- state_revision
- ownership_epoch
- first_generated_at
- last_active_at
- updated_at
- 主键为 instance_id、chunk_x、chunk_y

#### instance_infinite_chunk_domain

- instance_id
- chunk_x / chunk_y
- domain
- payload_version
- state_revision
- payload
- updated_at
- 主键为 instance_id、chunk_x、chunk_y、domain

固定 domain 建议包括 tile_delta、monster、container、resource、overlay。不要把 chunk 坐标拼进 ledger domain 名；flush ledger 仍以实例、固定 domain、ownershipEpoch 聚合，一次任务批量携带多个 dirty chunk。

持久化原则：

- 基础 terrain、surface、structure 不逐格落库。
- 没有动态变化的 chunk 最多保留一行生成元数据，不产生 2304 行地块数据。
- payload 只保存与基础生成结果不同的稀疏 delta 和一次性内容状态。
- runtime 的 chunk localIndex 不落库；恢复时按世界坐标或本地坐标重新映射。
- 刷盘快照在 tick 外构造，JSON 或二进制编码在 flush/staging 路径完成。
- 写入同时校验 ownershipEpoch 和 stateRevision，旧节点、旧快照和重复任务不能覆盖新状态。
- chunk 只有在 durable staging 或最终投影提交成功后才能因 dirty 而释放。
- DB 不可用时保留 dirty chunk、限制继续探索新区域并告警，不允许静默丢数据。

新增表或字段属于数据库 schema 变更，实施 Phase 4 前必须按项目高风险规则取得明确许可；本计划不执行 migration。

### 5.9 恢复顺序

服务重启或节点接管按以下顺序执行：

~~~text
读取 instance_catalog
  → claim/renew lease，取得 ownershipEpoch
  → 读取 instance_infinite_realm_descriptor
  → 校验 generatorVersion 与内容配置可用
  → 创建无 chunk 的无限实例 shell
  → 根据在线/离线玩家位置加载必要 chunk
  → 生成对应版本基础 chunk
  → 校验 baseHash
  → 叠加 chunk domain delta
  → 恢复实体、容器、占位和到期队列
  → 玩家接入并发送当前可见窗口
~~~

generatorVersion 不存在、baseHash 不匹配或 payloadVersion 不支持时必须 fail closed，将实例标记为不可恢复并阻止进入；不得改用最新生成器或默认平地继续运行。

### 5.10 网络同步

沿用 Bootstrap、MapStatic、WorldDelta、SelfDelta 分层，但为 streamed 地图增加明确空间元数据和紧凑地块窗口：

- Bootstrap / MapStatic：
  - 发送 spatialExtent=streamed、chunkSize、coordinateLimit、hideMinimap。
  - 只发送当前视野内可见地块，不发送 seed、完整 chunk、探索边界或隐藏锚点。
  - 初始可见窗口按当前半径最多约 21×21 格。
- WorldDelta：
  - 玩家移动后只发送新增可见格、变化格和离开可见集的移除 patch。
  - 动态玩家、怪物、容器、掉落继续走现有 AOI。
  - 地块使用数字 palette、局部坐标和连续区段编码，避免重复传完整 Tile 对象和字符串类型。
- 重同步：
  - payload 携带 instanceId、窗口 revision 和必要的 chunk revision。
  - 客户端发现缺口或迟到代际时请求受限流的当前窗口重建，不拼接未知旧 patch。

客户端生成基础地貌虽然可以减少包体，但会暴露隐藏地形和结构，也会形成客户端与服务端双实现风险，V1 不采用。

### 5.11 客户端状态与渲染

MapStore 增加 streamed 空间策略：

- 有界地图继续使用现有 tileCache 行为。
- 无限秘境使用 ChunkTileCache，以 chunk 坐标和 localIndex 存紧凑数组。
- 可见集、路径、命中和渲染通过 tile accessor 读取，不再把全部缓存复制成 renderTileCache。
- chunk 引用来自当前视野、淡出动画、路径和交互；无引用后按 LRU 与字节预算回收。
- hideMinimap=true 时不调用 rememberVisibleTiles、rememberVisibleTilePatches 或 rememberVisibleMarkers。
- 跨图、重连、instanceId 变化和 socket 代际变化时清空旧 streamed cache。
- signed 坐标必须贯穿相机、鼠标命中、触摸命中、路径预览、formation 预览和地图交互。
- 所有使用 mapMeta.width、height 判断边界的调用点必须改为统一 spatial extent helper；streamed 地图不得假设 x、y 大于等于 0。

现有 PixiMapRendererAdapter 已按视口创建 16×16 渲染块并在离开数帧后销毁，可保留其渲染生命周期；需要把输入从 ReadonlyMap<string, Tile> 改成局部 tile accessor 和 chunk revision，避免全历史 Map。

### 5.12 配置与内容生产

将当前 procgen-infinite-themes.ts 中的五个主题迁入正式内容契约：

- shared 定义 schema。
- config-editor 提供主题、地形阈值、散布、结构、可达性、内容锚点和移动策略编辑。
- 导入期校验所有 terrain、surface、structure、monster、container 和 contentSetId。
- 服务端启动期一次性编译为数字句柄和只读查表。
- 运行期不解析编辑器 JSON，不做 schema 校验，不按字符串扫描规则。
- 已发布 generatorVersion 的规则冻结。破坏性调整发布新版本；旧数据转换只能进入统一 GM 兼容转换目录并由运维显式执行、审计和回读。
- tools/procgen-demo 改为读取同一份已发布配置和生成版本，用于预览与 golden fixture 生成，但不共享生产缓存或权威状态。

### 5.13 GM 与可观测性

GM 只读诊断至少展示：

- 活跃/生成中/dirty/flush 中/失败 chunk 数。
- 当前 chunk 内存估算与实例总缓存字节。
- 生成队列长度、等待时间、P50/P95/P99。
- 生成失败、baseHash 不匹配和版本缺失计数。
- 局部寻路请求数、窗口面积、展开节点、失败原因。
- chunk flush backlog、最老 dirty 年龄、staging 字节和 DB 反压。
- MapStatic/WorldDelta 的 streamed 地块字节与每玩家发送率。
- 历史 chunk 数和探索范围只在 GM 查询时按索引统计，不装载地块。

Prometheus 等时序指标不得以 instanceId、chunkX、chunkY 作为高基数 label；单实例和单 chunk 明细只通过受鉴权 GM 查询按需读取。

必要运维操作包括冻结新 chunk 生成、重试 FAILED chunk、强制刷盘和安全卸载实例。所有写操作必须校验 lease、ownershipEpoch，写审计并回读验证。

## 6. 完整数据流

### 6.1 创建与首次进入

~~~text
入口玩法产生创建意图
  → 服务端校验玩家、队伍、冷却和 feature flag
  → 事务性写入 realm descriptor 与 instance_catalog
  → claim 本节点 lease
  → 提交原点及保护环 chunk 生成任务
  → Worker 返回基础数组、锚点、baseHash
  → 主线程校验并叠加空或已有 delta
  → 注入稳定返回传送点和允许的内容
  → connectPlayer 写入占位
  → MapStatic 只发送当前可见窗口
~~~

失败策略：

- descriptor 或 catalog 写入失败：实例不创建，不消耗进入资格。
- 原点生成或可达性校验失败：实例保持不可进入，记录诊断；不临时换 seed。
- 玩家连接中断：实例按正常空闲和 flush 规则回收。

### 6.2 移动、寻路与跨 chunk

~~~text
客户端点击已知目标
  → 客户端检查已知范围与 48 格上限，仅做预览
  → C2S 导航意图
  → socket handler 鉴权、覆盖同类旧意图
  → tick 外构建局部 path window
  → 目标相邻 chunk 缺失时提交有界预取
  → 生成就绪后物化路径命令
  → tick 内按 movementPolicy 最多推进 1 格
  → 服务端检查地形、动态阻挡和目标 occupancy
  → 原子迁移占位与实体 chunk 索引
  → SelfDelta / WorldDelta 增量同步
~~~

安全约束：

- 未加载或未验证 chunk 一律不可走。
- 客户端预览成功不代表服务端必须接受。
- 同一玩家只保留最新可覆盖导航意图，生成等待有超时和取消。
- 跨图、死亡、战斗打断或实例 fenced 时取消待处理路径 lease。

### 6.3 AOI 与地块同步

~~~text
玩家坐标或视线阻挡 revision 变化
  → chunk-local shadowcasting 查询
  → 生成 visible coordinate set
  → 对比该玩家上次窗口 revision
  → 首次/重连发紧凑 MapStatic window
  → 普通移动发新增/变更/移除 tile patch
  → 客户端更新 ChunkTileCache
  → 只标记受影响 Pixi render chunk revision
~~~

静态地形没有变化且玩家未移动时复用现有 player view cache，不重复构造地块对象或完整矩阵。

### 6.4 动态变化、刷盘与休眠

~~~text
战斗/采集/容器/临时地块产生变化
  → 只标记对应 chunk 的固定 domain dirty
  → tick 外冻结 ChunkFlushSnapshot
  → 写 durable staging 或最终 chunk domain 表
  → ownershipEpoch + stateRevision 围栏提交
  → 成功后确认 dirty revision
  → chunk 无引用且无新 dirty 时释放运行态
~~~

刷盘期间发生新变化时，新 revision 继续保持 dirty，旧快照成功只确认它覆盖的 revision，不能把后来的变化误标为已持久化。

### 6.5 断线重连、跨图与重启

- 断线保留期内玩家位置仍属于服务端权威状态，相应 chunk lease 按在线/离线策略持有或转成恢复锚点。
- 超过保留期后，先持久化玩家位置和相关 chunk，再释放运行时引用。
- 跨图先确保目标 chunk active 和可占用，再提交玩家位置切换；失败时玩家保持原图。
- 重连只恢复玩家附近 chunk，不加载全部历史探索区域。
- 重启按 5.9 的 descriptor-first 顺序恢复；一次性内容以稳定 anchorId 和持久化状态去重。

## 7. 容量模型与验收预算

### 7.1 长地图样例

1024×256 格按 chunkSize=48 计算约为 22×6，即 132 个历史 chunk。

正确实现下：

- 无玩家时，这 132 个 chunk 不常驻进程内存。
- 没有动态变化的基础地块不进入 instance_tile_cell。
- GM 统计最多读取 132 行 chunk 元数据或数据库聚合结果。
- 玩家回到某处只加载当前所需的少量 chunk。
- tick、寻路和客户端渲染成本不因“曾探索过 132 个 chunk”上升。

### 7.2 内存预算

| 项目 | 验收上限 | 说明 |
|---|---:|---|
| 48×48 chunk 固定核心数组 | 64KiB | terrain、surface、structure、flags、occupancy、revision 等，不含实体 |
| 单 active chunk 完整运行态 P95 | 96KiB | 不含怪物和玩家业务对象 |
| 单个孤立玩家持有 chunk | 最多 9 个 | 视野、路径和保护环合并后的硬上限 |
| 5000 个完全分散玩家的 chunk 基础运行态 | 不高于约 5GiB | 最坏上界；共享邻近 chunk 时应明显更低 |
| 10000 个无人实例 | 0 active chunk，且不注册常驻 tick | 只保留数据库目录和有界调度索引 |
| 客户端无限地图缓存 | 桌面 32MiB、移动端 16MiB | 仅地图地块缓存，不含贴图资源 |

最终 5000 在线压测下，服务端 RSS 目标不超过 12GiB，为 Node、实体、协议缓冲、数据库池和操作系统保留至少 4GiB 余量。

### 7.3 时延与吞吐预算

| 指标 | 目标 |
|---|---:|
| Worker 单 chunk 生成 P95 | 不高于 100ms |
| 主线程单次 chunk 激活提交 | 不高于 4ms；超出则跨帧分批 |
| 局部寻路 P95 | 不高于 5ms，且展开节点不超过 4096 |
| 普通移动触发的新可见地块 | 只发进入视野的边缘增量，不发完整 chunk |
| 5000 在线稳定态总出口 | P95 不高于 24Mbps，保留 20% 突发余量 |
| tick | 保持现有 1Hz，整体 P99 不突破 200ms 预算 |
| 历史面积增长 | active chunk 不变时，tick 与寻路耗时斜率约为 0 |

连接风暴和首次进入不能与稳定态混为一项：需要独立的进入速率限制和生成队列反压，确保瞬时 bootstrap 不突破 30Mbps。

### 7.4 必测场景

1. 单实例持续探索 24 小时，历史范围达到或超过 1024×256。
2. 300、500 在线玩家的实际玩法模型。
3. 5000 在线玩家完全分散到不同实例/区域的敌对上界。
4. 5000 在线玩家集中在同一大秘境的 AOI 与占位热点。
5. 10000 catalog 实例、仅少量 active 实例的冷态恢复。
6. DB 延迟、断连和 flush backlog 下的 dirty chunk 保留与探索反压。
7. 生成 Worker 超时、崩溃、队列满和返回坏 hash。
8. 客户端连续移动 24 小时后的 heap、GPU 资源、动画状态和缓存字节。

- 浅色、深色、桌面和手机模式。
- 连续探索后缓存字节保持上限，滚动、输入和动画不被全量重建打断。
- Pixi 只重建受影响渲染 chunk，离屏 GPU 容器及时释放。
- 协议包体在 5000 在线模型下满足 30Mbps 预算。

推荐命令：

- pnpm build:shared
- pnpm audit:protocol
- pnpm verify:client
- 新增 client-infinite-realm-cache-proof
- 新增 streamed-map-packet-size-bench

成本：6～10 工程日。风险：中高。

### Phase 6：秘境内容与玩法接入

目标：在稳定流式底座上接入入口、出口、怪物、资源和奖励。

工作项：

- 入口玩法只提交创建/进入意图，不在 socket handler 直接造实例。
- 原点生成稳定返回 portal。
- semantic anchor 翻译为现有冻结 monsterId、container、resource 和局部事件。
- runtimeId、spawnKey、containerId 和 reward operationId 由 instanceId、generatorVersion、anchorId 稳定派生。
- 一次性内容和复生内容分别定义持久化语义。
- 首发禁用玩家建造、房间和风水；formation 是否开放单独做跨 chunk footprint 验证。
- 复用现有秘境等级、掉落和功法池前，先完成对应内容规则决策，不把无限地图基础设施与奖励数值硬耦合。

验证：

- 重复进入、重连、重启和 Worker 重试不会重复刷怪、重复开箱或重复发奖。
- 原点和返回出口永远可用。
- 内容只在玩家接近的 chunk 激活，不提前生成整片世界。
- 无玩家 chunk 的怪物 AI 不运行；到期状态按绝对 tick 恢复。

成本：5～10 工程日。风险：中高，取决于内容范围。

### Phase 7：GM、容量证明与灰度

目标：证明容量、建立故障处置路径后再开放生产入口。

工作项：

- 增加 GM 只读诊断、聚合指标和审计写操作。
- 运行 24 小时探索 soak、500 在线实际模型和 5000 在线敌对模型。
- 运行 10000 catalog 实例冷态恢复。
- 验证 DB 故障、Worker 故障、节点 fenced、lease 转移和优雅停机。
- feature flag 分阶段开放：内部账号→小比例实例→全部入口。
- 回滚时停止新建和新 chunk 生成，允许已有玩家返回出口并完成刷盘；不删除旧 generatorVersion 和存档。

完成门禁：

- 本计划第 7 节预算全部有报告和原始数据。
- 不存在随历史面积增长的 tick、寻路、刷盘或客户端 heap 曲线。
- pnpm verify:release:full 通过。
- 生产 GM 能解释生成、缓存、flush、网络或恢复瓶颈。

成本：5～8 工程日。风险：中。

### 总成本估算

单名熟悉当前架构的资深工程师，纯工程实现约 41～71 工程日，不含大规模内容生产和数值调优。

主要成本不在噪声生成器，而在：

1. 把 MapInstanceRuntime 的全图 cellIndex 假设隔离成空间后端。
2. 建立 chunk 级持久化、卸载和崩溃恢复。
3. 改造客户端缓存，保证长时间探索后仍有界。
4. 在 5000 在线、30Mbps 下证明局部同步和反压。

## 9. 验证矩阵

| 层级 | 必须证明 | 主要门禁 |
|---|---|---|
| shared | 版本确定性、signed 坐标、边界无缝、可达性、schema | pnpm build:shared + generator golden smoke |
| config-editor | 非法主题和内容在导入/启动前失败 | 编辑器 build/typecheck + schema fixture |
| server runtime | chunk 生命周期、占位、移动、FOV、局部寻路、无全图扫描 | compile、verify:quick、新增 runtime smoke/bench |
| network | 分层正确、patch 有序、包体预算、重同步 | pnpm audit:protocol + packet bench |
| persistence | descriptor-first、围栏、幂等、崩溃恢复、自动清理 | verify:release:with-db + 新增 DB smoke |
| client | 有界 cache、signed 坐标、局部 patch、移动端 | pnpm verify:client + 浏览器 proof |
| 运维 | 指标可解释、故障可恢复、feature flag 可回滚 | GM smoke + 24h soak |
| 发布 | 全链无回归 | pnpm verify:release:full |

测试夹具要求：

- 所有 seed 和 generatorVersion 固定。
- DB smoke 自动删除 realm descriptor、chunk state/domain、catalog、ledger、staging、玩家位置和审计数据。
- 内存测试必须显式触发 GC 或使用进程隔离，报告 RSS、heapUsed、arrayBuffers 和 GPU/Canvas 资源，不能只看单一 heap 指标。
- 压测同时报告平均值、P95、P99、队列等待、丢弃/拒绝数和 backlog 增长率。
- 未实际执行的门禁不得写成“已通过”。

## 10. 主要风险与处理

| 风险 | 为什么错 | 后果 | 处理 |
|---|---|---|---|
| 直接扩展 RuntimeTilePlane 到所有历史格 | 仍是单实例全局 cell 数组 | 内存线性增长和扩容长停顿 | 引入 chunk-local 空间后端 |
| 只调小寻路距离 | AsyncPathfindingService 仍构建 width×height 网格 | 首次寻路仍扫描整图 | 真正构建局部窗口 |
| 每 chunk 一个 MapInstance | 复制 tick、玩家、持久化和租约边界 | 10000 实例目标迅速失控，跨块战斗困难 | 一个逻辑实例加多个空间 chunk |
| 客户端拿 seed 自己生成 | 暴露未知地图并形成双权威实现 | 作弊、版本漂移、隐藏内容泄露 | 服务端只发可见窗口 |
| dirty chunk 先释放后异步刷盘 | 崩溃时没有可恢复真源 | 地块、掉落、奖励状态回滚或复制 | durable staging/提交成功后再释放 |
| 旧世界用新 generator 重算 | 同坐标基础地形改变 | 玩家卡墙、delta 错位、内容重复 | generatorVersion 永久路由和 hash 校验 |
| hideMinimap 等同于不缓存 | 当前会话 tileCache 仍累积 | 浏览器运行一天后内存上升 | streamed ChunkTileCache 强制淘汰 |
| 生成任务复用 Encoding Worker | 与 AOI 编码、寻路争抢 | tick 同步包延迟和 Worker 饥饿 | 独立有界 Procgen Worker Pool |
| 噪声无缝等同于可达 | 当前默认 seed 存在出生阻挡和局部割裂 | 玩家出生卡死或探索骨架断裂 | 安全区、宏区门位和生成后校验 |
| 按 chunk 坐标创建动态 ledger domain | domain 数量随探索历史增长 | DB 行和调度复杂度失控 | 固定 domain，payload 内批量多个 chunk |
| per-chunk 指标使用高基数 label | 指标序列随实例和坐标爆炸 | 监控系统自身成为瓶颈 | 时序聚合，明细走 GM 查询 |
| DB 故障时继续无限生成 | dirty chunk 无法回收 | 内存最终耗尽 | 保留 dirty、生成反压、入口限流和告警 |
| 全局 width/height 兼容假值 | 客户端和服务端仍按矩形裁剪 | 负坐标不可点击、路径和交互异常 | MapSpatialExtent 统一分支并审计所有消费者 |

## 11. 上线与回滚策略

- 新能力由生产友好的默认关闭开关控制。
- 所有数据库调整只做 additive schema；旧地图读取路径不改语义。
- 有界地图先经过 spatial store parity 门禁，再允许无限秘境代码进入主线。
- generatorVersion 一旦有实例使用就不能删除；回滚业务入口不回滚生成器读取能力。
- 灰度失败时：
  1. 禁止创建新无限秘境。
  2. 禁止激活新的未知 chunk。
  3. 允许在线玩家使用返回出口。
  4. 刷盘全部 dirty chunk。
  5. 安全卸载实例，不删除 descriptor 和 chunk 真源。
- 不修改 docker-stack.tencent.yml 等 stack 文件；如后续确需新增独立 Worker 部署角色，必须另行明确授权和制定部署计划。

## 12. 完成定义

只有同时满足以下条件，才能将“无限秘境”标记为完成：

- [ ] 现有有界地图行为通过空间后端等价门禁。
- [ ] generatorVersion、配置发布、golden fixture 和 baseHash 契约完成。
- [ ] chunk 生成、加载、引用、刷盘、卸载、重入和失败状态机完成。
- [ ] 局部寻路不会构建或缓存整实例网格。
- [ ] 每息移动步数和最大路径距离由服务端强制执行。
- [ ] 无小地图、无地图记忆、客户端 chunk cache 有硬字节上限。
- [ ] 服务端与客户端都支持 signed 世界坐标。
- [ ] 基础地貌不逐格落库，动态变化按 chunk 稀疏持久化。
- [ ] descriptor-first 重启恢复、lease/epoch 围栏和 stale write 拒绝完成。
- [ ] 1024×256、24 小时探索时内存和 tick 不随历史面积持续增长。
- [ ] 500 在线实际模型与 5000 在线硬上界均有容量报告。
- [ ] 30Mbps 出口预算、200ms tick 预算和 16GB 内存预算通过。
- [ ] 所有 with-db 测试自动清理。
- [ ] GM 可查看并处理生成失败、dirty backlog、版本缺失和内存反压。
- [ ] pnpm verify:release:full 实际通过。
