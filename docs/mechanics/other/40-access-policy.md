# 通用权限系统

## 1. 定位

通用权限系统为宝库、统法台及后续需要访问控制的资源提供统一的策略契约、服务端权威检测、资源保存协调、Socket 请求链和客户端编辑器。

宝库和统法台已经通过资源适配器完成接入，旧专用保存事件与客户端编辑器已经移除。宗门职位权限属于宗门治理契约，继续使用宗门自身的 `rolePermissions`、版本 CAS 和管理界面，不接入本系统。

## 2. 策略模型

每个资源可以声明最多 8 个权限槽位，每个槽位保存一份独立的 `AccessPolicy`。例如同一宝箱类资源可以声明“可拿”和“可看与可放”两个槽位，两项权限分别检测、分别保存，互不隐含。

通用默认策略为“无策略”，即任何玩家都可以使用；业务自身的距离、资产、状态、冷却和事务约束仍然生效。资源适配器可以为不同资源、不同槽位声明不同默认策略，例如一个槽位默认开放，另一个槽位默认仅所有者。

单个 `AccessPolicy` 支持：

- `owner_only`：仅资源所有者可用。
- `everyone`：无附加权限策略，所有玩家可用；距离、资产、状态等业务约束仍由业务系统独立校验。
- `conditional`：最多选择两种不同类别的条件。
- 两组条件通过 `any`（或）或 `all`（且）组合。
- 同一类别内部的多选项按“任一命中”处理，例如关系类别或宗门职位。
- 所有者始终放行，避免错误配置导致资源所有者失去管理能力。

通用编辑器默认开放六类条件：

1. 好友关系：道友、至交、师父、徒弟、仇家。
2. 同宗门：全部成员，或宗主、太上长老、副宗主、长老、内门弟子、外门弟子、杂役弟子。
3. 指定玩家：只能输入玩家序号；查询成功后显示角色名，保存时服务端重新解析稳定 `playerId`。
4. 角色名字：完全匹配、包含、前缀匹配、后缀匹配。
5. 境界：大于、小于、等于指定 `realmLv`。
6. 属性：大于、小于指定最终属性值。

`party` 是旧宝库权限迁移使用的兼容条件。新策略默认不能添加该类别；已迁移策略会正确回显并可原样保留，也可以由管理者改成六类正式条件之一。

## 3. 权威检测链

1. 业务资源水合策略并调用 `AccessPolicyRuntimeService.prepare`，得到预编译策略。
2. 编译结果使用 dependency bitmask 标记关系、宗门、队伍、身份、境界和属性事实需求。
3. 检测时只收集策略实际依赖的事实；无关系统不会被读取。
4. 同一资源多项权限使用 `evaluateMany` 共享一次事实快照。
5. 最终布尔裁定由 shared 纯函数完成，客户端不得自行决定访问资格。
6. 业务系统在权限通过后仍必须继续执行距离、状态、库存、资产、冷却、幂等和事务校验。

好友关系事实使用有界 LRU 风格缓存，默认五分钟过期，并在道友关系变更时立即失效。师徒、仇家等系统通过 `registerRelationProvider` 注册权威关系提供器，不把其他系统的存储规则硬编码到通用模块。

## 4. 修改与保存链

客户端使用以下低频单播请求：

- `RequestAccessPolicy`：读取资源权限快照。
- `RequestAccessPolicySet`：一次读取同一资源的全部权限槽位、显示说明、默认策略和当前策略。
- `ResolveAccessPolicyPlayer`：按数字序号解析玩家并回显角色名。
- `SaveAccessPolicy`：提交策略和 `expectedRevision`。

服务端保存流程：

1. 校验当前 socket 仍是玩家有效会话，并按操作类别限流。
2. 通过 `resourceType` 找到已注册资源适配器和槽位声明。
3. 读取一次业务权威资源状态并校验管理资格；多权限界面不按槽位重复定位资源。
4. 校验资源 revision 与策略 revision 一致，并执行乐观锁比较。
5. 批量按玩家序号查询身份，忽略客户端提交的 `playerId` 和角色名。
6. 同一资源的所有槽位在单进程内串行提交，避免业务适配器写回整个资源时不同槽位互相覆盖；业务适配器仍必须在自身事务、CAS 或实例独占边界中再次校验 revision。
7. 只有业务持久化成功后才返回新快照；新 revision 必须严格等于旧 revision 加一。
8. revision 冲突时返回当前权威快照，编辑器加载最新配置后再允许用户重新修改，避免反复提交旧版本或静默覆盖他人变更。

资源适配器负责：

- 声明权限槽位、界面名称、说明和每个槽位的默认策略。
- 定位资源和权限槽位。
- 判断谁能管理该资源。
- 在资源自己的持久化真源中提交策略。
- 保证重复、并发、失败和恢复时的 revision 语义。

通用模块不另建业务权限表，避免与建筑状态、法脉状态或其他资源真源形成双写。

## 5. 当前接入资源与兼容迁移

### 宝库

- `resourceType`：`treasure_vault`。
- `view_deposit`：界面显示“可看和可放”，同时裁定查看宝库与存入物品，默认 `everyone`。
- `withdraw`：界面显示“可拿”，裁定取出物品，默认 `owner_only`。
- 两项权限通过一次 `evaluateMany` 共享关系、宗门、队伍和玩家事实；查看与存入不会重复读取关系系统。

### 统法台

- `resourceType`：`technique_unification_platform`。
- `read`：界面显示“参阅”，裁定查看并参悟当前法脉，默认 `everyone`。
- `revision`：界面显示“修订”，裁定向当前法脉续录功法，默认 `owner_only`。
- 首次凝篇会把当时的两项通用策略冗余到不可变法脉元数据，仅用于“模板已发布、建筑尚未刷盘”时恢复绑定；建筑 `accessPolicies` 始终是当前可变策略真源。

两类建筑都只允许建造者在同实例、建筑已完工且距离不超过 1 格时打开权限编辑器和保存。策略写入实例建筑域，按槽位 revision 做 CAS，并在建筑域刷盘成功后返回保存结果。

旧建筑快照只在实例冷水合时单向转换：

- 新 `accessPolicies` 中合法的显式槽位始终优先，禁止旧字段覆盖新真源。
- 旧宝库的 `view` 与 `deposit` 合并为 `view_deposit` 时采用安全交集，保证不会扩大任一旧操作的访问范围；旧 `withdraw` 独立转换。
- 旧配置同时包含三类条件、无法无损压入“两组条件”上限时，转换为 `owner_only` 失败关闭。
- 旧统法台的好友层级和宗门职位转换为通用关系、宗门条件；无开放项时转换为 `owner_only`。
- 水合后的运行态和后续持久化只写 `accessPolicies`，不再双写旧字段。

## 6. 性能与稳定性

- 已水合策略按对象引用缓存编译结果；检测阶段不重复创建条件 `Set`。
- 指定玩家和多选条件使用 `Set` 查询，不做数组全量匹配。
- `evaluateMany` 合并依赖，只刷新一次属性并共享宗门、关系和身份事实。
- 关系缓存有 `32,768` 条上限，不允许无界增长。
- 资源键、请求 ID、指定玩家数量和条件数量都有硬上限。
- 非法 schema、未知资源、权限数据损坏、关系读取失败和持久化失败均失败关闭。
- 枚举数组必须全部合法；非法宗门职位不得被规范化成“同宗门全部成员”，非法关系类别也不得被静默忽略。
- 客户端请求带 request ID、超时和操作类型匹配，忽略迟到或串错的回包。
- 多权限资源只在打开管理界面时读取一次；每个槽位保留独立编辑器实例，切换页签不丢失草稿、指定玩家或输入状态。
- 权限事件属于主动请求的低频 Detail / Result 层，不进入 tick、AOI 或广播链路。

tick 热路径不得直接调用需要数据库关系查询的异步事实收集。若未来出现每息或更高频权限检测，业务必须在进入热路径前准备好 `CompiledAccessPolicy` 和内存事实快照，再调用 shared 纯检测器。

## 7. 后续业务接入步骤

1. 为资源定义稳定的 `resourceType`、`resourceId`，并声明一个或多个权限 `slot` 及各自默认策略。
2. 在业务水合阶段规范化已保存策略，并缓存 `prepare` 返回的编译结果；真正未配置的槽位使用声明默认值，损坏或未来版本数据必须失败关闭。
3. 注册 `AccessPolicyResourceAdapter`，实现资源级 `load`、`canManage` 和带槽位 revision 的 `commit`。
4. 单权限界面可通过 `AccessPolicySocketClient.load` + `AccessPolicyEditor`；多权限界面通过 `loadSet` + `AccessPolicyResourceEditor` 一次加载并按页签编辑。
5. 业务使用权限时调用服务端 `evaluate` 或 `evaluateMany`，不得消费客户端草稿。
6. 添加该业务的迁移、回读、并发冲突和权限矩阵 smoke 后，才能移除旧权限实现。
